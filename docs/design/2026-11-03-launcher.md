## Summary

- **What it is.** A small Node daemon written in TypeScript, one per host, that joins vecnet as a peer of the new kind **`launcher`**. Any agent asks it to start a coding-agent session by sending it a **`launch` job** (§5.6). The launcher starts the session through a **backend plugin**, then relays the job thread to the session and posts each finished turn back into the thread.
- **One session per job thread.** The requester (the parent) is the session's main channel (decision i). The operator can always step in. Nobody else reaches the agent unless the requester lists them.
- **Backends are plugins** behind one TypeScript interface. Max's bridges are used through their existing CLIs, unmodified (decision f). First plugins: **`t3`** (through `t3-bridge`), **`paseo`** (through `paseo-bridge`, plus the official `@getpaseo/client` later), **`codex-app-server`** (direct JSON-RPC) and **`acp`** (`@agentclientprotocol/sdk`). **Sandcastle** fits only as an optional later batch backend. It cannot sit under ACP as a sandbox layer.
- **Hosts.** T3 Code is the common runtime: `t3code.service` runs on xsm, x-tall, x-tuf and x-p35. Paseo and both bridges exist only on xsm. x-alpha and x-19 did not answer. So `t3` is the first plugin everywhere, and `paseo` is xsm-only.
- **Hub changes are small.** Phase 1 adds the `launcher` kind and a presence TTL for it. Jobs, threads and approvals already exist. Phase 3 adds the `launched` kind on top of issue 28's frozen API, plus one new endpoint that binds a launched peer to its job, so the hub can set `spawned_by`. It also adds a confinement rule for launched peers. All of it goes in a PROTOCOL amendment (§18) and a launcher checklist (§13.8).
- **Questions and approvals go to the parent bot** (decision c as revised 2026-11-03; this supersedes the operator default in the research doc and pag-chat's earlier agreement with it, section 4.3).
  - **Questions** come from an agent asking for clarification or a choice mid-task. They arrive as an ordinary message in the job thread. The parent answers in the thread, and the launcher feeds the answer back as the next input.
  - **Permission prompts** come from an agent asking "may I run this command, edit outside my workspace, or use the network?". They arrive as an `approval_request` addressed to the requester. Each one carries a machine-readable `launch.permission` object (kind, tool, command, paths, host, scope, backend_raw), so a parent such as pagd can check it against its own grants without parsing prose.
  - The parent can pick an **escalate** option to send the prompt to Max. Policy can route chosen requesters or dangerous categories to the operator directly. pagd stays the relay for pag-requested launches, and its card is the only surface Max sees for those.
  - Self-approval is possible by design. It is bounded by spawn-time policy (permission mode, project), the concurrency caps and the audit trail. Today most backends bypass permissions anyway, so **spawn-time policy is still the main control**.
- **Isolation.**
  - T3 and Paseo sessions run under Max's uid, both on xsm and on the build boxes (D2).
  - Only launcher-run agents (P4) get `vecnet-*` uids, `vlaunch-<job_id>` units and their own nftables egress chain (decision k).
  - All launches use `launch/<job_id>` branches. Sweep and reattach copy pag-chat's patterns, never its namespaces.
- **Model traffic goes through Max's proxies** (D3): LLMP for non-Claude harnesses, CLIProxyAPI for Claude. There are no per-uid model logins. Each backend is pointed at a loopback bridge, whose local key is useless off-box, while the real LLMP and CLIProxyAPI keys stay with the bridge (section 5.6).
  - x-tuf and x-p35 already run the LLMP bridge (`codex-llmp-adapter.service`); x-tall does not.
  - Non-Claude harnesses come first.
- **Volume.** About 200 launches a day must be fine. **Concurrency is bounded, not totals** (D4): per-launcher and per-requester caps on running sessions, plus issue 28's revised active-peer cap and `--creates-per-hour`.
- **Idle.** The default is a 2 h idle wrap-up (decision h). The rigorous version separates a **finished turn** (resumable) from a **stopped process** (resumable only through a transcript, if at all). Idle is measured only when no turn, approval, queued input or known background task is open. It uses two timers, *park* (30 min) and *settle* (2 h or 24 h), now the defaults (D8).
- **Accepted risk.** Any agent may launch (decision b), and on xsm any requester may use `full-access` (D1). So any enrolled peer can get code execution as Max, with read access to his credentials. Build-box T3 sessions also run as Max (D2). Max chose simplicity for now. The bounds are the concurrency caps, the project allowlist, parent or operator review where backends ask, and the audit trail (section 8).
- **Decisions and open questions.** Max's answers are in section 10 (D1–D9). The four remaining open questions are in section 11.

### 1.1 Matt Pocock's Sandcastle

| Fact | Value |
|---|---|
| Repo, package | `mattpocock/sandcastle`, npm `@ai-hero/sandcastle` |
| Licence | MIT |
| Maturity | Created 2026-03-17; v0.13.0 published 2026-11-02 (v0.12.0 was 2026-06-29); about 8.8k stars. Pre-1.0: its glossary lists renamed options ("old name"), so expect breaking changes |

| Cancel | `AbortSignal` kills the in-flight agent process; the worktree is kept |
| Native sandbox network | **Open, including the host's localhost** (its docs say so under "Containment") |

Sources: the repo README, `GLOSSARY.md`, `docs/guide/{core-concepts,agent-providers,agent-sessions,sandbox-providers,run}.md`, `package.json`, and the GitHub releases API.

**Verdict.**
- **Not a P1 backend.** Each turn is a fresh one-shot process. That gives no mid-turn steer and no live session, and no approvals at all, because Sandcastle's model is AFK with permissions skipped. It suits batch work, not a conversational thread.
- **Not the sandbox layer under the ACP backend.** A sandbox handle offers `exec(cmd, {onLine})`, `copyIn` / `copyFileOut` and `close`, with no documented stdin stream. ACP and app-server need a live bidirectional stdio peer for the whole session.
  - Its native `bwrap()` also leaves loopback open. On every surveyed host, T3's MCP endpoint listens on port 3773, so a sandboxed agent could drive T3.
  - On Ubuntu 26.04, `bwrap` also needs a root-installed AppArmor profile.
- **Optional later backend (P5): `sandcastle`.** Use it for "do this batch task and give me a branch" launches on build boxes:
  - `docker()` on an internal Docker network behind the launcher's egress chain;
  - `branchStrategy: {type: "branch", branch: "launch/<job_id>"}`;
  - each vecnet turn becomes `sandbox.run()` with `resumeSession`;
  - interrupt through `AbortSignal`.

  Pin an exact version. Docker exists on all four reachable hosts.

## 2. Architecture

### 2.1 Shape

```
            vecnet hub (fly.dev)
   ▲ POST /v1/messages, /ack, /receipts, /presence      │ GET /v1/events (SSE, outbound only)
   │                                                    ▼
┌────────────────────── launcher daemon (one per host, TypeScript/Node) ──────────────────────┐
│ hub client (shared with openclaw) → ingress ledger (node:sqlite) → policy gate (sender id) │
│        → session router (job_id ↔ thread_id ↔ SessionRef) → per-session lane (serial)     │
│        → backend registry ──┬── t3 plugin ──────── t3-bridge CLI ──▶ T3 MCP :3773          │
│                             ├── paseo plugin ───── paseo-bridge CLI (+ @getpaseo/client)   │
│                             ├── codex-app-server ─ codex app-server (stdio / unix socket)  │
│                             ├── acp ────────────── ACP agent subprocess via vl-shim        │
│                             └── sandcastle (P5) ── @ai-hero/sandcastle docker()            │
│ approval bridge · idle clock · reattach + sweep · presence heartbeat · metrics            │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **Identity.** One `launcher` peer per host, for example `launcher-xsm` and `launcher-x-tuf`.
  - **Phases 1–2:** a peer credential.
  - **Phase 3:** a principal credential owning the launcher peer and its `launched` peers [I28].
  - Stored like other CLI profiles (§12), mode 0600, readable only by the daemon's uid.
- **Transport.** A pull client (§13.1): SSE with long-poll fallback, outbound only. Hosts are behind NAT, and §14.7 forbids hub egress to private addresses.
- **Ledger.** `node:sqlite` in the daemon's state directory holds:
  - the SSE cursor;
  - ingress rows, deduped on `delivery_id`;
  - jobs (`job_id`, `thread_id`, requester, backend, `SessionRef`, state, launch intent and fence, timestamps);
  - per-session input buffers;
  - open approvals;
  - the turn cursor per session.
- **Lanes.** Messages for one session are handled strictly in order. Sessions run in parallel up to the caps (section 6).
- **Home.** `connectors/launcher/` in vecnet4, a pnpm package beside `connectors/openclaw/`, with the hub client extracted to a shared package. Plugins live in `connectors/launcher/src/backends/<id>/`, and out-of-tree plugins load by module path (section 2.3). Max accepted this home (D7).
- **Runtime.** Node ≥ 22.12, so it runs on xsm's 22.23.3 and x-tuf's 22.22.1 as installed. CI tests 22 and 24. `node:sqlite` needs Node ≥ 22.5 and prints an experimental warning on 22.
- **Unit.**
  - xsm: `vecnet-launcher.service` (systemd `--user`, Max's uid), because T3, Paseo and both bridges' tokens live there.
  - Build boxes: a system unit running as uid `vecnet-launcher` (section 5).

### 2.2 Message flow for one session

1. **Launch.** A `delivery` carries a `job_request` with `operation: "launch"`.
   1. Commit the ingress row and ack the cursor.
   2. Run the policy gate (section 6) against `sender` and the job input.
   3. Report `accepted`. Write the launch **intent** with a tag `vl-<job_id>`, then call `backend.launch()`.
   4. Record the `SessionRef` and report `running`.
2. **Thread message.** The router finds the session by `thread_id` and checks the sender may talk (section 3.2). It maps priority to start, steer, queue or buffer (section 3.3). It hands the input to the backend with the `delivery_id` as the idempotency key, then acks.
3. **Turn end.** The launcher posts one reply in the thread: the final assistant message, with metadata. It then posts `processed` receipts for each consumed delivery, or `failed` ones.
4. **Question.** A turn that ends in a question needs nothing special: its result reply *is* the question. A structured question (app-server `item/tool/requestUserInput`, ACP elicitation) goes through the `onQuestion` hook. The launcher posts a question message to the parent (section 3.4) and resolves the hook with the parent's reply.
5. **Permission request.** The plugin calls the `onPermissionRequest` hook with a normalised `LaunchPermission`. The approval bridge posts an `approval_request` to the parent, or to the operator when policy routes it there (sections 3.5, 4). It resolves the hook on the response, on escalation, or on expiry.
6. **End.** An idle wrap-up, a requester `settle`, a cancel or a backend loss ends the session. The launcher calls `settle()` and reports the terminal `job_status`.

### 2.3 Backend plugin interface

Plugins are ES modules that export `definePlugin(...)`. The daemon loads them from config:

```toml
[[backend]]
id = "t3"
module = "./backends/t3/index.js"   # or an absolute path / package name
[backend.config]
bridge_bin = "/home/xertrov/.local/bin/t3-bridge"
caller = "vecnet-launcher"          # t3-bridge --as; distinct from Grok Bot's "forge"
```

```ts
// connectors/launcher/src/backend.ts — the contract every plugin implements.

export type BackendId = "t3" | "paseo" | "codex-app-server" | "acp" | "sandcastle" | (string & {});

/** Normalised permission vocabulary; each plugin maps it to its backend's modes. */
export type PermissionMode =
  | "read-only"    // no writes, no commands with side effects
  | "ask"          // per-action approvals surfaced through onPermissionRequest
  | "auto"         // backend-mediated: sandboxed workspace writes, backend's own auto-review
  | "full-access"; // permissions bypassed (paseo presets today, codex full-access, claude bypassPermissions)

export interface BackendCapabilities {
  steer: boolean;                              // can change an in-flight turn
  queue: "native" | "launcher";                // who holds input sent mid-turn
  interrupt: boolean;
  approvals: "typed" | "ui-only" | "none";     // typed = surfaced to onPermissionRequest
  questions: "typed" | "text-only";            // typed = surfaced to onQuestion; text-only = a turn ending in a question
  resume: "live" | "transcript" | "none";      // after the agent process stops
  backgroundTasks: "observable" | "opaque" | "none";
  attachments: boolean;                        // can pass files into a turn
  workspace: "backend-worktree" | "launcher-dir";
  branchName: "settable" | "backend-chosen";
  permissionModes: readonly PermissionMode[];
  presets: readonly PresetInfo[];
}

export interface PresetInfo { id: string; provider: string; model: string; effort?: string; note?: string }

export interface LaunchSpec {
  jobId: string;                 // job_… ; also the idempotency key for launch
  tag: string;                   // "vl-<job_id>": stamped into title/metadata so sweep and reattach can find it
  title: string;
  prompt: string;                // job_request.instructions, plus the launcher's footer
  project: ResolvedProject;      // launcher-side alias resolved to repo root + base ref
  branch: string;                // "launch/<job_id>" when branchName is settable
  preset: string;
  permissionMode: PermissionMode;
  attachments: LocalFile[];      // blobs fetched by the launcher, never URLs with tokens
  env: Readonly<Record<string, string>>; // already scrubbed; never contains vecnet credentials
}

export interface ResolvedProject { alias: string; repoRoot: string; baseRef: string }
export interface LocalFile { path: string; name: string; mediaType: string; sha256: string }

/** Opaque, JSON-serialisable; persisted in the ledger and given back to reattach(). */
export interface SessionRef { backend: BackendId; host: string; id: string; extra?: Record<string, unknown> }

export type SessionState =
  | { kind: "starting" }
  | { kind: "turn_running"; turnId: string; since: string }
  | { kind: "idle"; since: string }                         // turn finished, process alive (resumable now)
  | { kind: "parked"; since: string }                       // process stopped, transcript resumable
  | { kind: "waiting_approval"; requestIds: string[] }
  | { kind: "ended"; reason: "settled" | "exited" | "lost"; resumable: boolean };

export interface TurnInput {
  items: Array<{ deliveryId: string; messageId: string; from: string; text: string; attachments: LocalFile[] }>;
}

export type SendMode = "start" | "steer" | "queue";
export interface SendResult { mode: SendMode; backendInputId?: string; turnId?: string }

export type TurnEvent =
  | { type: "turn_started"; turnId: string; at: string; consumed: string[] }            // delivery_ids
  | { type: "progress"; turnId: string; summary: string }                               // tool use, plan step; not posted by default
  | { type: "turn_finished"; turnId: string; at: string;
      outcome: "completed" | "interrupted" | "failed" | "refused" | "max_tokens";
      finalText: string; consumed: string[]; usage?: Record<string, number> }
  | { type: "state"; state: SessionState }
  | { type: "process_exited"; at: string; code: number | null; resumable: boolean };

export interface TurnCursor { value: string }   // plugin-defined; persisted per session

export interface ActivityReport {
  turnRunning: boolean;
  openApprovals: number;
  queuedInputs: number;                        // native backend queue, if visible
  backgroundTasks: { known: number; observable: boolean; detail?: string[] };
  lastActivityAt: string;
}

export type SettleMode = "wrapup" | "requested" | "cancel" | "lost";
export interface SettleResult {
  branch?: string; headSha?: string; commits?: string[];
  workspaceKept: boolean; transcriptRef?: string; summary?: string;
}

export interface PermissionRequest {
  requestId: string;                           // backend's id
  summary: string;                             // one line, <= 512 chars: becomes approval_request.question
  permission: LaunchPermission;                // machine-readable; section 3.5. The plugin fills it, the daemon validates and redacts it
  options: Array<{ id: string; label: string; grants: Grant }>; // backend options; the daemon may append "escalate"
  defaultOnExpiry: string;                     // option id: the deny/cancel option
}
export type Grant = "once" | "session" | "always" | "deny" | "deny_always" | "cancel";
export interface PermissionDecision { optionId: string; reason?: string; decidedBy: string /* peer_ id, or "expired" */ }

export interface AgentQuestion {
  requestId: string;
  blocking: boolean;                           // app-server isBlocking; ACP elicitation is always blocking
  questions: Array<{ id: string; header?: string; text: string;
                     options?: Array<{ label: string; description?: string }>;
                     allowOther: boolean; secret: boolean }>; // secret questions are never relayed (section 3.4)
}
export interface QuestionAnswer {
  answers: Record<string, string>;             // question id -> chosen label or free text
  answeredBy: string;                          // peer_ id, or "timeout"
}

export interface SessionHooks {
  onPermissionRequest(req: PermissionRequest, signal: AbortSignal): Promise<PermissionDecision>;
  onQuestion(q: AgentQuestion, signal: AbortSignal): Promise<QuestionAnswer>;
  onEvent(ev: TurnEvent): void;                // the daemon persists and acts; must not throw
}

export interface BackendHealth {
  ok: boolean; degraded?: string[];            // e.g. ["paseo-bridge-watch.service failed"]
  version: string; detail?: Record<string, string>;
}

export interface SessionHandle {
  readonly ref: SessionRef;
  state(): SessionState;
  send(input: TurnInput, mode: SendMode): Promise<SendResult>;   // idempotent on deliveryId
  turns(after?: TurnCursor, signal?: AbortSignal): AsyncIterable<{ cursor: TurnCursor; event: TurnEvent }>;
  interrupt(reason: string): Promise<void>;
  activity(): Promise<ActivityReport>;
  park?(): Promise<void>;                      // release the process, keep the transcript
  settle(mode: SettleMode): Promise<SettleResult>;
}

export type ReattachResult =
  | { found: "live"; handle: SessionHandle }
  | { found: "parked"; handle: SessionHandle }
  | { found: "none" };                         // the launcher settles the job as outcome_unknown

export interface Backend {
  readonly id: BackendId;
  capabilities(): Promise<BackendCapabilities>;
  health(signal?: AbortSignal): Promise<BackendHealth>;
  launch(spec: LaunchSpec, hooks: SessionHooks, signal?: AbortSignal): Promise<SessionHandle>;
  reattach(ref: SessionRef, hooks: SessionHooks): Promise<ReattachResult>;
  findByTag(tag: string): Promise<SessionRef | null>; // closes the gap between launch intent and recorded ref
  listOwned(): Promise<SessionRef[]>;                 // sessions carrying this launcher's tag prefix; for the sweep
}

export interface PluginContext {
  host: string;
  log: Logger;                                 // redacting logger; bodies and secrets never logged (§12)
  store: KeyValue;                             // namespaced to the plugin, in the ledger
  exec: (argv: string[], opts: { env?: Record<string, string>; stdin?: string; timeoutMs: number; signal?: AbortSignal })
          => Promise<{ code: number; stdout: string; stderr: string }>;
  readSecretFile: (path: string) => Promise<string>;
  now: () => Date;
}

export interface Plugin<C = unknown> {
  id: BackendId;
  configSchema: unknown;                       // JSON Schema; config is validated before create()
  create(config: C, ctx: PluginContext): Promise<Backend>;
}
export declare function definePlugin<C>(p: Plugin<C>): Plugin<C>;
```

**Rules plugins follow:**
- A plugin never sees vecnet credentials, the hub URL or raw Deliveries, only `TurnInput`.
- A plugin never decides policy. It reports `capabilities()`, and the daemon checks the request against both capabilities and policy before `launch()`.
- `send()` must be idempotent on `deliveryId`, for example t3's `clientRequestId`. After a crash the daemon may resend.
- `turns()` must be resumable from a persisted cursor, so a daemon restart neither drops nor double-posts a turn result.

## 3. The vecnet contract

### 3.1 The `launch` job

**Request.** A `SendRequest` with `kind: message`, `priority: wake`, exactly one recipient (the launcher peer; §2.2 `job_single_recipient`), and no `thread_id`. Every launch starts its own thread.

```json
{
  "idempotency_key": "launch-review-pr-91-1",
  "recipients": ["peer_LAUNCHER_XSM"],
  "priority": "wake",
  "thread_title": "Review PR 91 (t3/sol)",
  "locked_participants": true,
  "history_access": "from_join",
  "max_depth": 64,
  "expires_at": "2026-11-06T00:00:00.000Z",
  "content": {"text": "Launch request: Review PR 91"},
  "job_request": {
    "version": 1,
    "job_key": "review-pr-91",
    "operation": "launch",
    "instructions": "<the prompt, <= 16 KiB; bigger briefs go in attachments>",
    "input": {
      "backend": "t3",
      "project": "vecnet4",
      "base_ref": "master",
      "preset": "sol",
      "permission_mode": "auto",
      "title": "Review PR 91",
      "idle": {"wrapup_after": "2h"},
      "relay_from": [],
      "reply_priority": "wake_idle",
      "deliver": {"push_branch": false}
    }
  }
}
```

**`input` fields** (launcher convention; the hub does not validate `input`, §5.6):

| Field | Required | Meaning |
|---|---|---|
| `backend` | yes | Plugin id, or `"any"` to let the launcher pick by preset |
| `project` | yes | A launcher-side alias mapped to a repo root. It is never a path from the requester, so a request cannot point an agent at `~/.ssh` |
| `base_ref` | no | The branch or commit the worktree starts from (default: the project's default) |
| `preset` | yes | Backend preset (model, effort, provider), from `capabilities().presets` |
| `permission_mode` | yes | `read-only`, `ask`, `auto` or `full-access`; must be within the requester's ceiling (section 6) |
| `title` | no | Session title; the launcher prefixes it with `vl-<job_id>` |
| `idle.wrapup_after` | no | Idle duration before wrap-up, at most the launcher's maximum; default 2 h (decision h) |
| `relay_from` | no | Extra peer ids whose messages in this thread reach the agent (section 3.2). Default empty |
| `reply_priority` | no | Priority of turn-result replies; default `wake_idle` |
| `deliver.push_branch` | no | When true, the launcher (not the agent) pushes `launch/<job_id>` to the project's remote at settle |

**Loop fields.**
- `max_depth` may be up to 64 (§6 range); a fresh message may set it. A launch should set 64, which gives about 30 round trips before the thread needs an operator reply or a continuation (section 3.8).
- `expires_at` bounds the session's wall-clock life. Replies cannot raise it.
  - Today's hub accepts any future value on a fresh message (`internal/hub/loop.go` `buildLoop`), while §6 says only "sender MAY lower it".
  - Max decided (D5): a fresh message's `expires_at` is capped at **7 days**, stated in the amendment and enforced in `buildLoop` (H5). A launch therefore sets at most now + 7 d, and `max_session_lifetime` (section 6) must not exceed it.

**Idempotency.** Three layers:
1. The hub's `idempotency_key` (per sender, 24 h): a retried send creates nothing.
2. The hub's `(thread_id, job_key)` dedupe: a retry into the same thread returns the same `job_id`.
3. The launcher's ledger keys on `job_id` with a unique constraint. A redelivered `job_request` (same `delivery_id`, or a replay after a cursor reset) never launches twice. Before calling the backend, the launcher writes a launch **intent** row with tag `vl-<job_id>`. If it crashes between the backend call and recording the `SessionRef`, reattach calls `findByTag()` and adopts the session.

**`job_status` transitions** (§5.6 table; `sequence` strictly increasing):

```text
requested (hub) ──policy ok, slot reserved──▶ accepted ──session started──▶ running ──▶ succeeded
      │                                          │                           │   └──▶ failed
      └──policy refusal / cap──▶ failed          └──launch error──▶ failed    └──cancel──▶ (cancellation_requested) ──▶ cancelled
```

| State | When | `output` (≤ 8 KiB) |
|---|---|---|
| `accepted` | Policy passed and a slot is reserved | `{host, backend, preset, permission_mode}` |
| `running` | The backend returned a `SessionRef` | `{session_ref, branch, workspace, link}`; `link` is a `t3-thread://…` or Paseo agent id, for humans |
| `succeeded` | Wrap-up, requester `settle`, or the agent finished and settled normally | `{ended: "idle_wrapup" \| "settled", turns, branch, head_sha, commits[], pushed, summary}` |
| `failed` | Policy refusal (`{error: "policy_denied", reason}`), cap (`{error: "cap_reached", details: {limit, running}}`), backend error, or a session lost after restart (`{error: "outcome_unknown"}`; never re-run) | as named |
| `cancelled` | The requester posted `job_status: cancelled`. The launcher interrupts and settles, then reports | `{branch, head_sha, workspace_kept}` |

The job stays `running` for the session's whole life, because the table has no `running → running`. Per-turn state travels in reply metadata, and in phase 3 in the launched peer's presence.

### 3.2 One session per job thread; who can talk

- The job thread *is* the session's conversation. This follows openclaw's "one session per vecnet thread" (R25). The launcher never moves a session to another thread on its own.
- **The requester is the main channel** (decision i). Its messages in the thread reach the agent.
- **The operator** can always reach the agent. Max's messages are relayed with a `From: operator` prefix, and §16.1 resets depth for them.
- **Peers in `relay_from`** are relayed. Everyone else's messages are acked and get a `processed` receipt with note `not_relayed`; no reply is posted, so there is nothing to loop on.
- **Requesters should create the thread with `locked_participants: true`** (§16.3), so only the requester and the operator can add participants. The launcher does not depend on this: the relay rule above is its own gate, keyed on the authenticated `sender`.
- Relayed messages enter the agent as quoted data with a one-line header (`[vecnet] from <name> (<peer_id>), msg_…`). The launcher never presents them as system or developer instructions.

### 3.3 Turn relay

**Priority mapping.** Priority does not change what a pull client sees (§5.2), so the launcher applies it:

| Priority | Session idle | Turn running |
|---|---|---|
| `wake` | Start a turn | **Steer** where `capabilities.steer` (t3 `mode: steer`, app-server `turn/steer`). Otherwise queue. ACP may cancel and re-prompt only if the launcher policy sets `wake_interrupts = true` (default false) |
| `wake_idle` | Start a turn | **Queue** behind the running turn: native queue (t3 `mode: queue`) or the launcher's buffer, sent as one turn when the current one ends |
| `hold` | **Buffer**; don't start a turn. The buffered text is prepended to the next turn's input | Buffer |

Approval responses and control messages (section 3.6) are never relayed as turn input.

**Ack and receipts.**
- Ack the cursor once the input is durably handed to the backend, or durably buffered in the ledger (§5.1 `accepted`).
- Post `processed` for every delivery a finished turn consumed (`consumed[]`). Post `failed` (note: outcome) when the turn failed or the session ended before consuming it.
- Drop `receipt` and `presence` Events before waking anything (§13.1).

**Turn results.** One reply per finished turn:
- `in_reply_to`: the last consumed message.
- Text: the final assistant message. Over 4 KiB it is auto-spilled (§2.2 step 6).
- `metadata`: `{"launch.turn": "completed|interrupted|failed|refused|max_tokens", "launch.turn_id": "…", "launch.job_id": "job_…", "launch.consumed": ["msg_…"]}`. These are not `vecnet.*` keys, so §14.5 allows them.
- Priority: `reply_priority`.
- Before posting, a best-effort redaction pass scans for known credential formats (t3-bridge's `redaction.mjs` patterns are a starting set).
- Progress events are not posted by default. Posting deltas would burn depth and the thread budget.

### 3.4 Questions from the agent (the primary path)

A launched agent that needs clarification or a choice asks its **parent bot**, the requester. It never asks Max directly (decision c, revised). Questions are conversation, so they travel as ordinary messages, not approvals. An approval has fixed options and closes on the first answer; a question may need free text, a follow-up, or a "neither, do X instead".

- **A turn that ends in a question** needs no mechanism. Its turn-result reply (section 3.3) is the question, the parent's reply in the thread is the next turn's input, and the session waits as `idle` meanwhile.
  - The launch prompt's footer tells the agent: "If you need a decision from your requester, end your turn with one clear question; your requester will answer in this conversation".
  - Idle timers keep running, so an unanswered question ends in wrap-up like any other idle session.
- **A structured question**, when the backend surfaces one: app-server `item/tool/requestUserInput` (questions with ids, headers, options, `isOther`, `isSecret`, `isBlocking`); ACP `elicitation/*` where the client advertises it; a Claude `AskUserQuestion`-style prompt where the adapter surfaces it (unverified for `claude-agent-acp`).
  1. The plugin calls `onQuestion`.
  2. The launcher posts a `kind: message` to the thread. The text lists the questions and their options. It carries `metadata["launch.question"] = {v: 1, question_id, blocking, questions: [{id, header, text, options: [label…], allow_other}]}`, and priority `wake` to the requester.
  3. The parent answers with a reply `in_reply_to` that message. Its text is mapped to the answers: an option label, or free text where `allow_other`. With several questions, the parent may instead send `metadata["launch.answers"] = {question_id, answers: {id: value}}`.
  4. The launcher returns the answer to the backend (app-server `ToolRequestUserInputResponse`) and acks the reply, which is consumed as a question answer, not as turn input.
  5. **Timeout:** a blocking question gets 30 minutes by default. It is then answered `"no answer from requester; use your best judgement and say what you assumed"`, and the launcher posts a note. A non-blocking question is answered the same way at once if the parent has not replied by the time the backend moves on.
- **Secret questions are never relayed.** If `isSecret` is set (a password or token, say), the launcher answers `"secrets cannot be provided through vecnet"` and posts a note to the parent. Credentials must never travel in message bodies (section 8).
- Only the requester, the operator and `relay_from` peers can answer (section 3.2). A reply from anyone else is not relayed.

### 3.5 Permission prompts and the `launch.permission` object

**Routing.** A permission prompt becomes a vecnet `approval_request` in the job thread:
- addressed to the **requester** by default;
- `escalate_to_operator: true`, so the hub's phase-2 escalation (§9) forwards it to Max at the halfway point once that ships;
- with the backend's own options plus an **`escalate`** option when the route allows it.

Section 4 covers who answers and why. The approval's `question` is a one-line summary. **The requested permission itself is machine-readable**, so a parent such as pagd can check it against its own grants without parsing prose. pag-chat asked for this: pagd plans to approve only when it is untainted and the permission is within its own grants, and to escalate to Max otherwise.

**Where it travels.** `metadata["launch.permission"]` on the `approval_request` Message.
- `approvalRequest` is a closed schema object (`additionalProperties: false`), whereas metadata is free-form and sender-owned (≤ 8 KiB). So this needs **no hub or schema change**, and `launch.*` keys are allowed (§14.5).
- The launcher keeps the object under 6 KiB.
- If the backend's raw request is larger than the cap below, the launcher truncates `backend_raw` and attaches the full JSON as an attachment (`application/json`, name `permission-raw.json`), referenced by `backend_raw_sha256`.
- Promoting the object to a typed optional `approval_request.permission` field is a possible later schema amendment (Q4, section 11).

**Shape** (`v: 1`; JSON Schema in the §13.8 launcher checklist):

```ts
interface LaunchPermission {
  v: 1;
  kind: "exec" | "edit" | "network" | "mcp_tool" | "other";
  backend: BackendId;
  backend_method: string;          // e.g. "item/commandExecution/requestApproval", "session/request_permission"
  tool?: string;                   // agent tool name: "Bash", "shell", "apply_patch", "mcp:<server>/<tool>"
  command?: {
    argv?: string[];               // only when the backend supplies argv; never synthesised
    line?: string;                 // the command string as the backend gave it
    cwd?: string;
    shell_operators: boolean;      // launcher-computed: line contains ; | & && || $( ` > < etc., so it is not one argv
  };
  paths?: Array<{
    path: string;                  // absolute, after realpath where it exists
    access: "read" | "write" | "delete" | "move";
    in_workspace: boolean;         // launcher-computed against the session's workspace root
  }>;
  host?: { name: string; protocol?: string; port?: number };
  scope: "once" | "session" | "always"; // the broadest grant any offered allow-option would give
  options: Array<{ id: string; label: string; grants: Grant }>; // mirrors approval_request.options, with meaning
  workspace_root: string;
  outside_workspace: boolean;      // launcher-computed: any path or cwd outside workspace_root
  reason?: string;                 // the agent's own stated reason: untrusted text
  backend_raw: unknown;            // the backend's original request params, redacted, <= 4 KiB serialised
  backend_raw_truncated: boolean;
  backend_raw_sha256?: string;     // the full raw request, attached when truncated
  redacted: boolean;               // true if redaction changed command, paths or backend_raw
  fidelity: { command: "argv" | "line" | "none"; paths: "exact" | "partial" | "none"; host: "exact" | "none" };
}
```

**Rules for consumers:**
- `fidelity` says how far a parent can rely on each field. A parent that checks grants should treat `none` or `partial` as "cannot verify", and the same goes for `redacted: true` or `shell_operators: true` when its grants are argv-based. In those cases it should escalate.
- Launcher-computed fields (`in_workspace`, `outside_workspace`, `shell_operators`, `fidelity`) are the launcher's statement. `reason` and anything inside `backend_raw` come from the agent and are untrusted.
- The parent must check that the `approval_request` came from the launcher peer for this job, which is the job's recipient. A message from anyone else carrying `launch.permission` is ignored, because metadata is sender-owned.

### 3.6 Control from the requester

These are authorised by sender id only. A requester-sent message with `metadata["launch.control"]`:

| Value | Effect |
|---|---|
| `interrupt` | Interrupt the running turn and keep the session; the reply reports `launch.turn: interrupted` |
| `settle` | End the session normally: interrupt if needed, `settle("requested")`, job `succeeded` |
| `extend` | Reset the idle clock, once per message |
| `continue_in` | Rarely needed; see section 3.8 |

Cancel is the standard §5.6 path: the requester posts `job_status {state: "cancelled"}`. The operator may send any control. Controls from anyone else are ignored, like non-relayed messages.

### 3.7 Presence

- **Launcher peer (phases 1–2).** It reports its own presence every 5 minutes and on change:
  - `idle`: accepting launches;
  - `working`: sessions running, capacity left;
  - `blocked`: at the cap, or every backend unhealthy;
  - `offline`: clean shutdown.
- `capabilities[]`: `launch:<backend>`, `preset:<backend>/<preset>`, `host:<host>`, `mode:<permission_mode>` (the modes any requester may use).
- `quota`: `{"max_sessions": 4, "running": 1, "per_requester": 2, "backends": {"t3": "ok", "paseo": "degraded"}}`.
- Requesters choose a launcher from the directory by kind `launcher` and these tags. Tags are self-reported and never authorise anything (§14.1).
- **TTL.** Add a per-kind TTL of 15 minutes for `launcher`, like `session` (`internal/hub/presence.go`), so a dead launcher shows `unknown` quickly.
- **Launched peers (phase 3)** report:
  - `working` during a turn;
  - `idle` between turns;
  - `blocked` while an approval is open, or for app-server `active` with `waitingOnApproval`;
  - `offline` after settle.

  That makes `wake_idle` meaningful per session for push-capable peers.

### 3.8 Loop control

- Every relayed message, turn reply, approval request and response, and `job_status` counts against depth and the thread budget (§6, R20). With `max_depth` 64 that is about 30 exchanges.
- Operator replies reset depth (§16.1), so Max can always revive a session.
- **Continuation.** When a requester wants a long session past depth, budget or TTL, it sends a **new launch job** in a new thread with `input.continue_job: "job_…"`. Only the original requester may continue its job, and only while the session is not ended.
  - The launcher moves the session's relay to the new thread. It reports the old job `succeeded` with `{ended: "continued", continued_in: "thr_…"}`.
  - This is the requester's explicit act, and the per-peer limit of 20 new threads per hour (§16.2) bounds it.
  - The launcher itself never mints a thread to dodge depth.
- The connector breaker (§6) applies to the requester ↔ launcher pair. After 12 alternations in 10 minutes without a human, the launcher stops relaying and asks the operator with an `approval_request` ("continue relaying?").

### 3.10 Phase 3: `launched` peers through issue 28

- **Setup.** The operator creates a principal for each launcher and moves the launcher peer under it (`peer move`). Then it sets limits with issue 28's revised flags (D4):
  - `vecnet principal limits <prn> --kinds launched --max-peers <max_open_sessions + 8> --creates-per-hour 60`. For xsm that is `--max-peers 32`.
  - `--max-peers` counts **active** peers only; disabled peers do not count [I28 revised]. Open sessions, including parked ones, keep their peer enabled, so the active count tracks open concurrency (section 6). The margin of 8 covers peers created during a settle race.
  - `--creates-per-hour` (default 60) bounds a create/disable loop. About 200 launches a day averages 8–9 an hour, with room for bursts.
  - Issue 28's default is off. `launched` is just another allowlisted kind, and `operator`, `source` and `session` stay forbidden.
- **Per session**, after the backend reports `running`:
  1. `POST /v1/peers {kind: "launched", name: "<host>/<job_id short>", idempotency_key: "<job_id>"}` with the principal credential. The response is `201 {peer, idempotency_key}`. No per-peer secret exists [I28]: the launcher sends `as` the new peer.
  2. `POST /v1/jobs/{job_id}/session-peer {peer_id}` (H7). The hub checks four things: the caller is the job's recipient or its principal; the peer is `created_by` that same principal; its kind is `launched`; and it is unbound. It then sets `spawned_by = {launcher: <job recipient>, requester: <job requester>, job_id}` from its own records. The response is 200; 409 if already bound, 403 `not_recipient`, 422 `invalid_value` otherwise. It writes an audit row and emits `directory_updated`.
     - This builds `spawned_by` from authenticated facts the hub already holds, **without touching issue 28's frozen create shape**.
  3. The launcher adds the launched peer to the job thread. It posts as the launched peer `in_reply_to` the launch message. The requester created the thread, but the launcher is a participant and addressing a new peer adds it. **Conflict:** with `locked_participants: true`, only the creator or the operator may add participants. Decided (D6): H7 grants that one add, so the job's recipient may add its own bound session peer to the job thread.
  4. From then on, turn replies, approval requests and presence go `as` the launched peer. The launcher peer itself posts only `job_status`.
- **End.** After settle, the launcher sets the peer `offline` and disables it with `PATCH /v1/peers/{id} {disabled: true}` [I28]. A disabled peer no longer counts toward `--max-peers`, so retired sessions never block new launches (D4). Their directory entries stay for provenance; pruning them is an optional operator chore, not a capacity need.
- **Refusals.**
  - **429 `peer_cap_reached`** (active cap): the launcher is over its concurrency anyway. This should not happen if `--max-peers ≥ max_sessions`, and it is reported like `cap_reached`.
  - **429 `peer_create_rate_limited`** (with `details.retry_after_seconds`): the session still starts, using the phase-1 behaviour (replies `as` the launcher peer, job output `session_peer: null`). The launcher retries the create and bind once after `retry_after_seconds`, then moves the session onto the new peer.
  - Either way a launch is never refused merely because a peer could not be minted.
- **Agent-initiated sends** (optional): a local MCP tool the launcher offers inside the session, sending `as` the launched peer. Confinement (H9) limits it to the job thread and its participants. The agent sees a tool, never a secret.
- **Trust.** Launched peers are always untrusted [26 pag-chat review]. A requester's taint never raises them, and they never become `user-remote`. Consumers that ignore `spawned_by` still fail closed, because `launched` is an unknown kind to them.

## 4. Approvals

### 4.1 What they are

A coding agent working on its own sometimes reaches a step its permission mode does not allow. Examples: running a shell command such as `rm`, `curl` or `cargo publish`; editing a file outside its workspace; or reaching the network.

A backend in an asking mode **pauses the agent and asks for permission**. In T3 or Paseo that is a card in their UI. Through vecnet it becomes an `approval_request` message (§9): a one-line question, 2–8 options such as "allow once / allow for session / deny", an expiry, and the machine-readable `launch.permission` object (section 3.5). The first valid answer from an addressee unblocks the agent; no answer by the expiry means deny. Questions (clarifications, choices) are not approvals; they go to the parent as conversation (section 3.4).

### 4.2 Who answers: the parent bot, by default

- **The requester (parent bot) by default** (decision c, revised 2026-11-03). The launcher addresses the `approval_request` to the requester in the job thread:
  - options are the backend's own (each with its `grants` in `launch.permission.options`), plus an **`escalate`** option;
  - `escalate_to_operator: true`;
  - priority `wake`;
  - `expires_at` now + 15 min.
- **Escalation.** The parent picks `escalate` when it cannot judge the request, for example when `fidelity` is too low or the command is outside its own grants. The launcher then posts a new `approval_request` to the **operator**:
  - the same `launch.permission`;
  - the backend options without `escalate`;
  - priority `wake`, which fires Max's notification webhooks (§9);
  - `expires_at` now + 60 min.

  The agent stays blocked meanwhile. When the hub's phase-2 escalation ships (§9, not built yet), an unanswered parent prompt is also forwarded to Max at the halfway point.
- **On parent expiry**, the default is the backend's deny option. The agent continues its turn, and the thread shows the expiry. Policy may set `on_parent_expiry = "escalate"` instead.
- **Operator override.** Max is not an addressee of the parent's prompt, so the hub would refuse his `approval_response` (403 `not_addressed`). Instead, the launcher accepts a reply to the prompt from the **operator only**, carrying `metadata["launch.decision"] = "<option label>"`. It resolves the backend with that; the vecnet approval then simply expires, and any later parent answer gets a "superseded" note.
- **Policy can route straight to the operator** (per launcher, per requester, per category):

```toml
[approvals]
route = "requester"               # default (decision c, revised)
parent_expires = "15m"
on_parent_expiry = "deny"         # or "escalate"
operator_expires = "60m"

[approvals.to_operator]           # these go to Max directly; recommended defaults (Q1, section 11)
requesters = []                   # peer ids not trusted to approve their children's prompts
outside_workspace_writes = true   # launch.permission.outside_workspace with write/delete/move access
privileged_exec = true            # sudo/su/doas/pkexec, or paths under /etc, /usr, ~/.ssh, ~/.config
unverifiable = false              # fidelity "none": left to the parent, which can escalate itself

[relays]
pagd = ["peer_…"]                 # pag-requested launches (decision j)
```

- **pagd stays the relay for pag-requested launches** (decision j).
  - The prompt goes to the pagd bot peer that requested the launch, with `escalate_to_operator: false` and **no** `escalate` option. pagd escalates inside its own surface: its approval card to Max stays the single surface for those launches.
  - pagd's announced rule fits the machine-readable field: approve only when it is untainted and the permission is within its own grants, otherwise ask Max on its card.
- **Mechanics.**
  - The launcher accepts a response only from the addressee, which the hub enforces (`not_addressed`), or the operator override above.
  - It maps the `decision` label back to the backend option id it recorded.
  - Every decision is recorded in the ledger (`approval_id`, the permission, the route, `decided_by`, the decision, the latency), and the request and response stay in the thread (hub audit: `send`).
  - Approvals count against depth (R20); operator responses reset it (§16.1).

### 4.3 Why this supersedes the operator default

The research note (§2.5 and §3.5(c)) and pag-chat's review (msg_01M6ER5S4BTZD1MN8ME06ZX5FV: "the operator by default; a requester approves only when a launcher policy names it explicitly") routed prompts to Max unless the requester was a configured human-decision relay. Max changed that on 2026-11-03, for these reasons:
- **The parent is assumed honest, and it has the context.** It wrote the brief, and it knows what the task needs. So it is better placed than Max to recognise a bad command and correct the agent, for example "don't delete `target/` by hand, run `cargo clean`".
- **Operator-by-default makes Max the bottleneck** for unattended work. In practice that pushes launches onto bypass presets, which is how paseo-bridge runs today, so nobody reviews anything. Parent review is strictly more review than bypass.
- **It does not breach pag-chat's anti-goal.** That anti-goal forbids a peer message counting as *Max's* approval. Here a parent's decision is recorded as the parent's (`decided_by: peer_…`) and is never presented as Max's.
- **Max stays reachable** through `escalate`, policy routes, the operator override, and (later) the hub's escalation. pag-requested launches keep pagd's single card.

**Risks.** Self-approval is possible by design: a parent can approve its own child's request, and a compromised or careless parent can approve something bad. The bounds are:
- the spawn-time policy (permission-mode ceiling, project allowlist, backend and preset);
- the per-launcher and per-requester concurrency caps;
- direct-to-operator categories;
- the audit trail (ledger plus thread history);
- on build boxes, the uid and egress isolation.

### 4.4 What each backend supports today

Which `launch.permission` fields each backend can fill is in section 3.5.

| Backend | Per-action approvals reach the launcher? | Today's reality |
|---|---|---|
| T3 via t3-bridge | **No.** T3's MCP has no answer-approval tool; an `approval-required` thread waits for someone in the T3 UI | The launcher can only post a "waiting for approval in T3" note if `t3_thread_read` exposes that state (to verify in P1) |
| Paseo via paseo-bridge | **No.** Every preset bypasses permissions (Codex `full-access`, Claude `bypassPermissions`, Muse `allowAll`, Cursor `auto_accept`) | `@getpaseo/client` has `pendingPermissions` and `respondToPermission`, so it becomes possible in P3 with a non-bypass preset |
| Codex app-server | **Yes, typed**: command, file change, permissions and user-input requests; `accept / acceptForSession / decline / cancel` | P4 |
| ACP | **Yes**: `session/request_permission` with the agent's options | P4 |
| Sandcastle | **No**: AFK with permissions skipped. Claude `permissionMode: "auto"` and Codex `approvalsReviewer: "auto_review"` use an AI reviewer, not a person | P5 |

### 4.5 Spawn-time policy is still the main control

Until P3/P4, almost every launched agent runs with its permissions bypassed or auto-reviewed. Even afterwards, the parent that approves is the same peer that asked for the launch. So **what a launched agent can do is decided at launch**, by the launcher's policy, keyed on the authenticated requester id:
- which backends and presets it may use;
- which **permission mode** it may use: the ceiling;
- which projects;
- how many sessions it may run at once.

The launcher refuses any request above the ceiling with `failed {error: "policy_denied"}`; it never downgrades silently. Section 6 gives the defaults.
- Decided (D1): on xsm, **any requester may use `auto` or `full-access`**, to keep things simple for now. The ceiling still limits projects and backends, and concurrency caps still apply.
- With parent approvals, `ask` becomes a useful default on backends with typed approvals (app-server, ACP, Paseo SDK). The parent sees each risky step instead of none.

### 5.2 Units and processes (launcher-run backends, P4)

1. The daemon asks the wrapper `vl-unit start <job_id> <slot> <backend>`. The wrapper validates its arguments, then runs `systemd-run --unit=vlaunch-<job_id> --property=User=vecnet-aNN --property=WorkingDirectory=/srv/vecnet-launcher/ws/<job_id> --property=RuntimeMaxSec=<expires_at bound> --property=CPUQuota=200% --property=MemoryMax=8G --property=MemorySwapMax=0 …` with a scrubbed environment and the pinned agent command. The 2-core and memory caps match Max's build etiquette.
2. The unit runs `codex app-server --listen unix://…` directly, or `vl-shim <acp command>`.
3. The daemon connects to the socket. The socket is group-readable by `vecnet-launcher` only.
4. The unit outlives a daemon restart. The daemon reattaches by socket file, as pag-chat's `reattach.ts` does by pid or socket file.

### 5.3 Egress chain (decision k)

`table inet vecnet_launch`, chain `output` hooked at filter priority, matching `meta skuid` in the set `@vecnet_agent_uids`:
- **Accept** established traffic, DNS to the configured resolver, the loopback model bridge port (`127.0.0.1:18080`, section 5.6; agents never reach LLMP or CLIProxyAPI directly), and `github.com` / forgejo over HTTPS for fetches.
- **Drop** all other loopback ports. This blocks the host's own T3 at `127.0.0.1:3773`, the bridges' other ports and the paseo daemon.
- **Drop** RFC 1918, link-local and ULA ranges, which blocks T3 on x-tuf and x-p35 at `0.0.0.0:3773`, other build boxes and xsm.
- **Log and drop** everything else, rate-limited.

Pushes of `launch/<job_id>` are done by the daemon uid, not the agent, so agents need no write credential for remotes. The table is separate from pag-chat's, so neither side's reload clobbers the other. Box-setup ownership on x-tall is Q3 (section 11). The chain covers only launcher-run uids: T3 sessions on build boxes run as Max (D2) and are not filtered.

### 5.4 Reattach and sweep (copying pag-chat's patterns)

- **Outcome fence.** The order is: intent row → backend launch → record the ref. A row with an intent but no ref goes through `findByTag("vl-<job_id>")`; if still missing, the job is `failed {error: "outcome_unknown"}`. **The launcher never re-launches.** This is pag-chat's `reattach.ts` rule.
- **On start**, for every non-terminal ledger row, call `reattach(ref)`:
  - `live`: resume `turns()` from the stored cursor; post only turns not yet posted, keyed by `launch.turn_id`.
  - `parked`: keep the job `running`; the next message resumes it.
  - `none`: report `failed {error: "outcome_unknown"}`.
- **Sweep** (`vlaunchsweep`, hourly):
  - Look at `listOwned()` plus `vlaunch-*` units plus `/srv/vecnet-launcher/ws/*`.
  - Anything with a `vl-` tag or `vlaunch-` prefix and **no** live ledger row is an orphan. Settle it after a 24 h grace and log it.
  - Remove a socket or runtime file only when its owning unit is gone, the analogue of `agent-sweep.ts`'s "pid dead, start time checked".
  - Never touch anything without the launcher's prefix or tag. That includes Max's own T3 threads, Grok Bot's `forge` launches and every `pag-*` resource.
- **Share code, not runtime state** [26 pag-chat review]: copy the patterns from `@pag/machines` (`ssh.ts`, `reattach.ts`, `agent-sweep.ts`). A shared supervision package can come later.

### 5.5 Honest limits: xsm and T3 on the build boxes

On xsm (T3 and Paseo) and on the build boxes (T3, D2), agents run as Max's uid, with whatever permission mode the launch uses. No uid boundary or egress rule applies.
- A `full-access` agent on xsm can read `~/.config/vecnet/config.toml` (Max's operator credential), SSH keys and every token in his home. On a build box it can read Max's files there and reach the LAN, including other hosts' T3 on port 3773.
- Max accepted this for now (D1, D2): any requester may use `full-access`.
- The real bounds are:
  - concurrency caps;
  - the project allowlist;
  - parent or operator review where a backend asks;
  - the audit trail;
  - later, P4's launcher-run isolation (`vecnet-*` uids plus the egress chain).

  P4 is the step that removes Max's credentials from an agent's reach.

## 6. Who may launch, and the caps

- **Any enrolled agent may launch** (decision b). The launcher's policy defaults to allowing any `sender`, with two exceptions:
  - `launched` peers may not launch in phase 3 without an explicit grant. Confinement (H9) blocks `job_request` from them anyway, which prevents spawn trees.
  - `source` ids cannot send at all.
- **Authorise on the authenticated `sender` only** (§14.1, §14.3). Never on names, content, `origin`, `ingress`, kind or `capabilities`.
- **Caps** are the safety bound. Defaults:

```toml
[limits]
max_sessions = 6                 # unparked sessions per launcher (xsm); build boxes 3–4 by cores
max_open_sessions = 24           # including parked sessions (no process); bounds launched peers too
max_sessions_per_requester = 3
max_open_sessions_per_requester = 12
launches_per_requester_per_hour = 30   # burst guard only; totals are not bounded (D4)
max_idle_wrapup = "8h"           # requester may ask for less or more up to this
max_session_lifetime = "72h"     # also bounds expires_at (hub cap 7 d, D5) and RuntimeMaxSec

[ceiling.default]                # any agent (decision b)
backends = ["t3", "paseo"]
permission_modes = ["read-only", "ask", "auto", "full-access"]   # D1: any requester, auto or full-access; "ask" pairs with parent approvals
projects = ["vecnet4"]                      # explicit allowlist of aliases

[ceiling."peer_OPERATOR"]
permission_modes = ["read-only", "ask", "auto", "full-access"]
projects = ["*"]

[relays]
pagd = []                        # pagd bot peer ids: approvals to them carry no escalate option, escalate_to_operator false (section 4.2)
```

- **Concurrency, not totals (D4).** About 200 launches a day must work, and nothing caps the daily total. The required concurrency is roughly launches per day × mean slot-hold time ÷ 24 h.
  - A slot is held from launch until the session parks: the turns plus 30 minutes of idle (D8).
  - With a mean hold of about 1 h, 200 a day needs about 8–9 unparked sessions fleet-wide.
  - xsm's 6 plus 3–4 on each of x-tuf, x-p35 and x-tall gives about 15–18 unparked sessions.
  - Parked sessions cost no process, only a ledger row, a workspace and (in P3) an active launched peer. `max_open_sessions` bounds them, and the settle timer (2 h or 24 h) drains them.
- Over a cap, the job gets `failed {error: "cap_reached", details: {limit, running, open}}`. There is no hidden queue in P1, so a requester sees back-pressure at once.
- The hub's per-peer limits (§16.2: 60 sends per minute, **20 new threads per hour**) also apply. Every launch starts a new thread, so one requester can start at most 20 launches an hour, about 480 a day. That is fine for 200 a day spread over several requesters. A single requester that needs more asks the operator for `vecnet peer limits <peer> --threads-per-hour N`.

## 7. Session lifecycle and idle

### 7.1 For now (decision h)

When a session has been idle for 2 h, the launcher wraps it up:
- `settle("wrapup")`;
- job `succeeded {ended: "idle_wrapup"}`.

Idle means no running turn, no open approval, no buffered or queued input, and no known background task. A requester `extend` resets the clock.

### 7.2 The rigorous version (for a later decision)

**Two different "stopped" states.**

| State | Meaning | Resume cost | Per backend |
|---|---|---|---|
| **Finished turn** (`idle`) | The agent answered and is waiting; the process and its context are live | Free and instant | T3 thread idle; Paseo `activeTurn == null`; app-server `ThreadStatus.idle`; ACP `session/prompt` returned `end_turn` |
| **Stopped process, resumable** (`parked`) | The process has gone, but a transcript lets the backend rebuild context | A cold start, plus a context reload (and a cache miss) | T3 restarts the provider on the next send; app-server `notLoaded` → `thread/resume`; ACP only with `session/load` / `session/resume`; Sandcastle `resumeSession` |
| **Stopped process, not resumable** (`ended`, `resumable: false`) | Nothing to resume | Only a new launch with a brief | ACP agents without load/resume; any backend after its transcript is archived |

A coding agent does not come back by itself after its turn ends. **The exception is background work**:
- Claude Code background shells;
- Codex background processes, which app-server exposes as `process/outputDelta` and `process/exited`;
- T3's `schedule_task` scheduler, which "runs even when no turn is active".

An agent with background work may start a new turn when it completes. So:

**Idle is measured only when all of these hold** (from `activity()`):
1. no turn running;
2. no open approval (app-server `activeFlags` includes neither `waitingOnApproval` nor `waitingOnUserInput`);
3. no native queued input (app-server `thread/queue/changed`, T3 queue) and an empty launcher buffer;
4. no known background task, where `backgroundTasks == "observable"`;
5. no relayed message in the window.

Where background tasks are `opaque` (T3 today, Paseo today), the launcher cannot prove quiescence. It uses the longer settle timer and says so in the wrap-up output.

**Two timers instead of one:**
- `idle_park` (default 30 min, D8; only where `resume` is `transcript`): release the process (`park()`, or app-server thread unload) and keep the workspace and transcript. The job stays `running`, and the next message resumes. This saves RAM and slots without ending anything.
- `idle_settle` (default 2 h for opaque backends, 24 h for observable parked ones; D8): `settle("wrapup")` and report the job `succeeded`.
- Optional **wrap-up turn** before settle, opt-in per job (`idle.wrapup_turn: true`): one final prompt, "commit your work on `launch/<job_id>` and summarise in ≤ 10 lines". Its result becomes the job summary. It is opt-in because it costs a turn and depth.

**What "settle" means per backend:**

| Backend | Settle | Workspace afterwards |
|---|---|---|
| t3 | `t3-bridge settle` (`t3_thread_organize` settle); interrupt first if running | Kept (T3's worktree); swept by the launcher only if tagged and older than the retention period |
| paseo | `paseo-bridge settle <id>` (archives the agent **and** its worktree) | Removed by Paseo. Commits must be on `launch/<job_id>`, or pushed, before settle |
| codex-app-server | `turn/interrupt` if needed → `thread/archive` → stop the `vlaunch-<job_id>` unit | Kept for retention (default 7 d) under `/srv/vecnet-launcher/ws/`, then swept |
| acp | `session/cancel` if needed → close or delete the session if supported → stop the unit | As app-server |
| sandcastle | Abort if running → `close()` | The worktree is preserved by Sandcastle |

Because Paseo's settle deletes the worktree, the launcher makes sure the branch has the work before calling it: it checks `git rev-parse launch/<job_id>`, and pushes if `deliver.push_branch` is set.

## 8. Security

1. **Launched agents are untrusted, always.**
   - Their output is content (§14.2).
   - A requester's trust or taint never raises them.
   - Phase 1 marks them by the launcher kind; phase 3 by the `launched` kind plus hub-set `spawned_by`.
   - Receivers must not act on launched output as instructions.
2. **Authorisation from the sender id only.** The requester's prompt and input are untrusted data to the launcher. A prompt cannot widen its own ceiling, choose a path (projects are aliases) or pick approvers (the approval route is launcher config).
3. **Credentials never travel in message bodies.**
   - The vecnet credential lives only in the daemon's profile. It is never in an agent's environment (the env is scrubbed of `VECNET_*` and of `*_API_KEY`, `*_AUTH_TOKEN`, `*_BASE_URL` unless a preset allowlists one) and never in a prompt.
   - Blob tokens are used by the daemon to fetch attachments into local files. URLs carrying tokens are never passed to agents.
   - pag-minted per-job tokens wait for a secret channel, so pag-requested launches wait too [26 pag-chat review].
4. **Model auth is the launcher's own, through Max's proxies (D3).**
   - LLMP for non-Claude models and CLIProxyAPI for Claude, both reached through a loopback bridge (section 5.6).
   - There are no per-uid model logins and no provider OAuth copied to agents.
   - Agents hold at most a local bridge key, which works only on loopback. The LLMP consumer key and the CLIProxyAPI client key stay with the bridge.
5. **Logs.** Message bodies and secrets never enter the daemon's logs (§12); a redacting logger is the default.
6. **The hub stays a hub.** It holds no backend credentials and supervises no processes (G6 in [RES]).
7. **Blast radius.**
   - xsm and build-box T3 (Max's uid): not bounded by permission mode, since any requester may use `full-access` (D1, D2). The bounds are the project allowlist, parent or operator review where the backend asks, and the audit trail (section 5.5).
   - Launcher-run sessions on build boxes (P4): uid plus egress chain plus unit resource caps plus `RuntimeMaxSec`.
   - Everywhere: concurrency caps plus hub rate limits.

**What gets built**
- A TypeScript/Node **launcher** daemon, one per host, in `connectors/launcher/` (D7). It is a vecnet pull client (SSE) with a `launcher` peer credential, and a principal credential in P3.
- Agents start sessions with a `launch` job: the prompt in `instructions`; backend, project alias, preset, permission mode and idle policy in `input`.
- Idempotency comes from `idempotency_key`, `(thread_id, job_key)` and a ledger intent row tagged `vl-<job_id>`.
- `job_status`: `accepted` → `running` (with session ref) → `succeeded`, `failed` or `cancelled`. Lost sessions end `outcome_unknown` and are never re-run.

**Conversation model**
- One session per job thread. The requester is the main channel, the operator can always step in, and other peers are relayed only if listed in `relay_from`.
- Priority: `wake` steers (or queues), `wake_idle` queues, `hold` buffers into the next turn.
- One reply per finished turn, `processed` receipts, `max_depth` 64, `expires_at` at most 7 d (D5). Continuation is a new launch job only the requester can send.

**Backends as plugins**
- One `Backend` / `SessionHandle` interface: capabilities, launch, send (start, steer or queue), turns stream, interrupt, activity, park, settle, permission and question hooks, health, reattach, sweep listing.
