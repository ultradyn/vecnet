## Decisions (2026-11-05)

Max settled the following choices; they stand subject to the later AS D2C authority amendment above. Throughout the normative contracts below, “operator” means a caller with the checked bootstrap-root authority for that operation, not an operator-kind test, credential prefix, role or grant bypass. “Operator-only” restrictions require that explicit authority and the stated target protections. Only AS bootstrap/backfill can seed roots; later root-derived authority must use its checked grant-management contract. No role expansion or additional launch administrator is implied.

1. **Delegated boundaries:** support own-principal and hub-wide grants. Default to own-principal and `delegable=false`; hub-wide authority is an explicit operator-created exception, never inferred from peer kind.
2. **MCP discovery:** keep a stable static tool listing. Unavailable calls return clear `forbidden` / `insufficient_scope` errors naming the needed capability or OAuth scope. Expose safe effective permissions and guide text.
3. **Delegated policy writes:** operator ceilings bound scopes, destinations, kinds and numerical limits. Delegates cannot expand authority up to hub defaults.
4. **Human invitations retain paste blocks:** keep human-initiated CLI/web invitations by operators or delegated humans, including stdout and `--copy`. Add 0600 `--output-file` as an option; do not retire or break the existing invitation flow. Max's rationale: "I'd just be catting a file and pasting that in anyway. Since the tokens are easy to use, if the agent doesn't claim it then we revoke the one that didn't get used or was used by someone else (in the worst case)." MCP never receives invite tokens or credentials: an agent requests a pending action, a human confirms, and that human receives the paste block. Make single-use/TTL, status, revoke/re-issue and one-step revocation of an unexpected enrolment first-class across CLI, MCP (status and recovery only, never tokens) and web.
5. **Write preconditions:** accept legacy unconditional operator writes with warnings for one release, then require revisions. New CLI/MCP writes use preconditions immediately. Name the release and end date at build time.
6. **TUI sequence:** this build adds read-only observation and policy/permission reads. Immediately after it merges, dispatch full TUI admin forms as a separate worktree build using the follow-up brief below.

## Security contracts

1. **One model: explicit grants, no inferred authority from kind.** AS grants are the sole authority. The bootstrap principal holds its explicit grant set; existing operator-kind peers keep powers only through AS's copied, revocable peer-subject grants. Principal/peer/operator/session/dot/grokbot kind alone grants none. Consume AS principal/peer subjects; native principal admin grants do not ambiently authorize peer credentials or OAuth-bound peers. Resolve OAuth's bound peer from server-verified state (currently `Caller` may be principal-shaped with a `PeerID`), never from an argument or `as`. Effective peer grants, including preserved operator-peer grants, are checked for that subject. Existing P-own provisioning, group and self powers keep their narrow contracts; ownership is not admin authority. Frozen scope/default-scope reads derive from grants; compatible scope writes update grants and their cache in the same transaction, never an independent send/admin policy store. Missing/expired grants deny; legacy empty-allow/open wire syntax represents explicit unrestricted grants only when authorized, never absence of grant rows.
2. **Capabilities and boundaries.** Use `admin:peers`, `admin:scopes`, `admin:limits`, `admin:principals`, `admin:routes`, `admin:sources`, `admin:teams`, `admin:groups`, `admin:deliveries`, `admin:threads`, `admin:blobs`, `admin:notify`, `admin:subscriptions`, `admin:observe`, `admin:audit`, `admin:prefs`, `admin:notices`, `admin:credentials`, `admin:grants` in AS's closed capability list. Consume AS `Grant` subjects/resources/access/expiry; write includes read. The AP request/view boundary `{kind:own_principal,principal_id:<server-fixed id>}|{kind:hub}` maps to AS resource `principal` with that fixed ID or `hub`; ancestry/envelope and `delegable=false` are coordinated extensions of the same grant model, not independent grant rows evaluated by a second resolver. Omitted boundary defaults to own-principal; never silently substitute hub when an operation cannot support own-principal. Only checked operator authority can originate a hub boundary; any child retains that explicit root provenance and obeys attenuation. Own-principal means **the grant subject's** current principal at issuance, not a principal supplied by the caller. Store its ID to prevent move-following. Principal mutation, teams, hub preferences/notices/notify, global observe/audit and unarchive begin hub-only; do not invent ownership for hub-global objects. Routes belong to peers/principals; sources map through their target. Deliveries, subscriptions and threads need ownership queries: own-boundary mutation only when every affected peer/participant belongs to that principal. Otherwise deny. Global audit/activity are never offered under own boundary in v1; filtered resource audit is a separate future contract.
3. **Boundaries alone do not prevent scope escalation.** Operator-managed delegation envelopes carry explicit destination peer sets and numerical ceilings for peer/principal limits and permitted kinds. A delegated `admin:scopes` writer may change only peers in its boundary, and may authorize sends only inside that ceiling. Empty allow is legacy open wire syntax: reject open policy under a finite ceiling, and do not confuse it with deny-all or treat missing grants as open. Expand team/group targets at evaluation; fail closed on mixed/out-of-envelope membership. Persist the envelope as an extension of the shared grants/policy projection and enforce its intersection at send time too, so later membership changes cannot widen it. Defaults receive the same constraints; created peers inherit the ceiling, including AS's colleague-owned-agent ceiling. Grant targets cannot include the operator peer or peers whose credentials would confer greater authority. AS refuses new `--kind operator` peers (422); bootstrap/backfill preservation is not a new creation path. Reserved infrastructure kinds, changes to operator credentials, and issuance for any subject with authority above the issuer retain operator-only restrictions; credential administration may never mint a route around the grant ceiling. Preserve `NeverProvisionable` for principal provisioning. A delegated limits writer cannot raise provisioning or send caps above its envelope. Hub-wide unrestricted editing requires an explicitly unrestricted operator grant. Test denied recipients and changing memberships, not just target IDs.
4. **Delegation is attenuated and revocation is live.** An `admin:grants` write grant is necessary but insufficient to grant/revoke: issuer must also hold each capability with `delegable=true`, at least the requested access and a boundary/envelope superset. Own cannot grant hub, read cannot grant write, and finite ceilings cannot become unrestricted. Record one parent authority grant per child in the shared foundation; multiple requested capabilities create separate children. Parent revoke/expiry invalidates descendants immediately through the checked ancestry, including at tools/call and an open stream's next batch. Nonoperators cannot edit their own authority, revoke ancestors, touch unrelated grants or alter operator credentials. Only checked bootstrap-root authority can originate root-derived grants/expand envelopes; kind alone cannot do so, and foundational root seeding belongs to AS. A peer move invalidates grants and policies tied to its old principal; it never carries delegated authority into another principal. Disabling/rotating a subject preserves the existing credential-revocation behavior, and disables grant use immediately.
5. **Authorize inside transactions, not just middleware.** Existing `hub/admin.go` methods often have no caller and hardcode audit actor `operator`; existing `/v1/admin` middleware rejects everyone else. Do not simply loosen that prefix. Introduce caller-aware service entrypoints taking a verified actor context; authenticate the prefix, deny unclassified admin routes, then authorize operation/target and recheck grant ancestry plus ownership within the mutation transaction. Retain legacy helpers only as private implementations. Audit actual actor, principal, OAuth client identifier where applicable, operation ID, target IDs, grant/parent IDs, result/reason and safe counts. Do not audit raw bodies, destination URLs, pasted malformed identifiers, secrets or tokens. Denials need a committed sanitized audit independent of a rolled-back mutation. Restrict read audit volume with a documented policy; always record sensitive reads and refused admin calls.
6. **OAuth is an extra gate.** Require both effective hub grants and explicit OAuth `admin:<domain>:read|write` scopes; write scope includes read for that domain only. Keep `vecnet` base scope. Add scopes to discovery, client validation, consent and tool security metadata. Existing `AuthorizationScopes` automatically adds Events scopes on consent; never add admin scopes there. A client explicitly requests them, a human explicitly consents, and current subject grants bound the result. Refresh can narrow, never add admin scopes; a new grant requires fresh consent. Revoking a hub capability takes effect despite an unexpired token. Native bearer `Principal.HasScope` returning true is only an OAuth bypass, not a capability grant. Events scopes remain independent. HTTP-native bearer authorization remains supported; no new requirement to accept OAuth on all HTTP routes.
7. **Stable tool lists; enforced forbidden.** Retain the existing static tools/list design. List tools with clear permission and safe-channel descriptions, filter sensitive values from schemas, and check authority on **every call**. A known but unauthorized tool returns tool-level `isError` with `{code:"forbidden",required_capability,required_access}`; missing OAuth consent uses existing `RequireScope` HTTP 403 / RPC -32003 `insufficient_scope` challenge naming the required scope. This gives a stable client cache and a clear way to request access; discovery is not authorization. Do not expose an allowed tool list as proof a call will succeed. Extend `vecnet_whoami` with safe effective capabilities/boundaries, and `vecnet_guide(topic:"admin")` with the user's grant/consent path.
8. **Safe credential channel: MCP requests, human invitation output.** For AP's agent/admin credential operations, a “one-time link” that itself redeems a secret is a bearer credential and is not safe model output. MCP credential-bearing create/invite/reinvite/rotate/link operations use a pending action. MCP returns only `{request_id,status:"awaiting_human",revision,review_path:"/ui/admin/requests/<id>",expires_at}`; request ID/path carries no authority and requires a separately authenticated human with both operation permission and `admin:credentials` at least as broad. Merely fetching a path never mints, rotates or consumes anything. Human reviews exact bound arguments, target, issuer and expiry and explicitly confirms in a protected UI POST. Then the server issues credentials to that human response only, including the invitation paste block, or accepts route/source keys through a protected form. MCP polling returns terminal status and safe resource metadata, never the token, link code, key, enrol command or human response. The human channel is a separately authenticated browser session with a server-issued CSRF secret; no caller-supplied `human=true` or MCP argument can assert it. MCP never exposes confirm/redeem as a tool for these admin requests. Final authorization rechecks issuer AND approver; no impersonation via a more powerful approver. Pending action is immutable, expires in 10 minutes, single-use, idempotent by issuer/key and request digest; no credential side effects before approval. This approval TTL is separate from the issued invite's TTL. A headless MCP client receives `human_action_required` plus the same non-secret request metadata. Human-initiated CLI/web invites by an operator or delegated human continue issuing directly through the authorized human surface and return the paste block; they do not require an MCP pending action. Existing raw-secret endpoints remain trusted human/CLI compatibility surfaces, explicitly marked in the manifest; MCP never calls them and discards nothing after minting. The separate AS Task 6 guest-prompt exception remains governed only by its recorded limits; it provides no exception for any AP tool or pending request.
9. **Human output compatibility and secret hygiene.** Human-initiated invitations retain stdout paste blocks, `peer invite --copy` and web copy/paste controls, including equivalent invite-issuing peer create/reinvite flows. Add 0600 `--output-file` as an optional delivery choice, with no retirement, mandatory file migration or compatibility break for invitations. Human confirmation of an MCP invite request provides the same paste block to the human only. For non-invite credential commands, use protected files/profile installation as planned; external route keys remain `--key-file` only, with existing permission checks. No secret argv/environment flags; MCP cannot pass server-local paths or request stdout/clipboard output. The protected human UI masks values until explicit reveal/copy, uses `Cache-Control: no-store`, no URL secrets, no analytics/storage/log captures; host/session-bound CSRF protection, Origin checks, no cross-origin framing, and explicit confirm. The intended human stdout/clipboard/paste block is the allowed invitation output, never an MCP result, audit, diagnostic or fixture transcript. Pending IDs can appear in model context because they cannot approve or redeem. Do not use vector messages or event logs to deliver credentials.
10. **Read-modify-write and redaction.** Dedicated config GETs return exact safe configuration, effective/default metadata, `revision` and ETag. Conditional writes use If-Match; missing precondition returns 428 `precondition_required`, stale revision returns 412 `revision_conflict`, no silent overwrite. For exactly one release, legacy unconditional operator writes remain accepted with an explicit deprecation warning; the following release requires revisions. Record the release/end date during implementation. Delegated writes and new CLI/MCP writes require preconditions immediately. Each scope set supplies both allow and deny arrays; a scoped CLI `--add-allow` convenience fetches, merges locally, conditionally replaces, and on conflict requires refetch/review. Never silently rebase a scope change. Secret-bearing route/notification URLs (userinfo, path tokens, query) are not safe metadata. Return scheme/host plus redacted display and presence flags; edits either preserve opaque existing fields server-side or use the protected human channel. Never return encrypted secret ciphertext as a substitute for a secret.
