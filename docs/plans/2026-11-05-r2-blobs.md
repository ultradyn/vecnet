# R2 Blobs with Direct Transfers and 24-Hour Expiry Implementation Plan

> **For agentic workers:** Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement task by task. Follow the house task/review gates in `docs/plans/2026-11-05-hub-notices.md`. Steps use checkbox (`- [ ]`) syntax. A `---` ends every task. This document is a plan; its creation does not authorize deployment or resource creation.

**Goal:** Fly-hosted hubs authorize private, signed transfers for new R2 attachments whose file bytes never traverse Fly, with exactly 24 hours of application availability. Local hubs retain their disk backend; existing hosted disk files remain grandfathered.

**Architecture:** Keep authorization, reservations, object state and message references in SQLite. The free-tier baseline has **no Worker**: clients and HTTP-capable MCP hosts PUT/GET directly on the private R2 S3 endpoint using stdlib SigV4 presigns. Sign exact Content-Length and a provider-enforced checksum; prefer SHA-256 only after the first real-bucket spike passes, otherwise use signed Content-MD5 with verified MD5+size identity and explicitly unverified client-declared SHA-256 metadata. R2 keys use grant IDs, with no cross-uploader dedupe. A custom download domain via a minimal free-plan Worker is an optional later task, never a baseline dependency and never a hashing service. Persistent message text and avatars remain database content, outside attachment expiry; existing Fly disk files are grandfathered without migration.

**Tech Stack:** Existing Go toolchain, `CGO_ENABLED=0`, Go stdlib `crypto/hmac`, `crypto/sha256`, `crypto/md5` (transfer checksum only), `encoding/xml`, `net/http`; vanilla browser modules; Node connector code. No AWS SDK or new Go module. No Worker/tooling in the baseline. Optional later custom-domain Worker uses only Web Crypto HMAC and streaming R2 GET, with separately pinned dev tooling.

## Current behavior and implications

- `internal/blob/store.go` streams to disk, hashes, dedupes globally, charges 25 MiB/file and 500 MiB/uploader/UTC day defaults, and records all uploaders. Its GC removes only **unreferenced** bytes; pins override TTL. Neither that TTL nor the seven-day HMAC read-token lifetime implements this requirement.
- `internal/httpapi/blobs.go` currently receives PUT bodies and serves seekable GETs with Range, `nosniff` and CSP sandbox. `internal/hub/blobs.go` authorizes a recipient token (including an enabled-peer check), operator, or history-visible thread participant. `checkAttachments` in `internal/hub/spill.go` prevents hash guessing from granting attachment access.
- `spill.go` stores full long text as a blob uploaded by `hub`, then emits a preview and `message.md`. `internal/hub/sources.go:IngestSource` also stores source raw JSON as an attachment. Both need an explicit durable message-data path before R2 is enabled.
- Contrary to the assignment's premise about avatars, `internal/hub/avatar.go` already normalizes images and stores PNG bytes in `avatars.png` in SQLite (migration `0016_peer_avatars.sql`). Preserve that behavior; do not migrate avatars to expiring storage.
- CLI `app.upload` in `internal/cli/commands.go`, `internal/opclient.Client.Upload/Blob` (also used by the TUI), web `api.js`, and connector `HubApi.putBlob/fetchBlob` are separate transfer entry points. There is currently no top-level `vecnet blob get` command; add it rather than referring users to a nonexistent command.
- MCP currently accepts 160 KiB decoded PUTs and returns 128 KiB base64 GET pages, deliberately stripping delivery read tokens. Maintaining those byte paths for remote attachments would violate the Fly constraint even at their present small caps.

## Decisions and wire contracts

### 1. Isolated objects, checksums and attachment identity

Add optional `blob_id` to the attachment schema and require it for new R2 uploads. IDs are server-generated `blo_` plus a 26-character Crockford base32 encoding of 128 cryptographically random bits (first character 0–7). Use a random-ID mint rather than timestamp ULIDs. IDs confer no authority. Each grant allocates one key `attachments/v1/<hub_namespace>/<blob_id>`; the namespace is random and persisted in SQLite. Keys contain no filenames, uploader IDs or client paths. **The key is the grant ID, never a content hash**, in both checksum profiles. No cross-uploader or cross-generation dedupe: independent 24-hour lifetimes and small short-lived files make dedupe savings minor, while isolation avoids existence leaks and retention coupling. Disk dedupe remains unchanged.

Checksum profile is pinned per grant and reported in authenticated capabilities, completion results, attachment wire and state projections:

- `sha256`: selected only if Task 0 proves R2 enforces the signed base64 `x-amz-checksum-sha256` against actual single-PUT body bytes. The wire `sha256` is verified by R2's enforced checksum and hub metadata checks; record `sha256_verified:true`, `integrity:{algorithm:"sha256",value:<hex>,verified:true}`.
- `md5`: selected if that SHA test fails but signed Content-MD5 succeeds. **Choose verified MD5+size as the hub identity**, scoped to blob_id; retain the attachment's existing `sha256` field solely as client-declared compatibility metadata, with explicit `sha256_verified:false` and `integrity:{algorithm:"md5",value:<base64>,verified:true}`. This keeps existing routes and old consumers working without advertising collision-resistant content addressing. New clients must display/consume the trust flag; hub ownership/visibility/attach/purge lookups use blob_id, never the unverified SHA as proof or a dedupe key. A claimed SHA tombstone can conservatively reject the claim, but cannot prove a fallback upload's content; document that limitation of hash-level purge. MD5+size detects transfer corruption, not malicious MD5 collisions.

An upload result is `{blob_id,sha256,sha256_verified,integrity,size,expires_at}`; attachment sends must match the persisted reference fields. Re-upload always makes a new ID/deadline, and old messages stay expired. Reject hash-only R2 requests with authenticated 422 `blob_id_required`; legacy hash-only disk and durable-message requests retain their lookup semantics. Bind new versioned delivery tokens to `(recipient,sha256,blob_id)`; v1 disk tokens never authorize R2. The SHA route segment in fallback mode is a compatibility label, not authorization or a verified identity.

### 2. Upload grant → immutable PUT → metadata verification → attach

1. `POST /v1/blobs/uploads` with bearer, `Idempotency-Key`, JSON `{size,sha256,content_md5,media_type}`. Require integer size 1..25 MiB, lowercase 64-hex SHA, canonical 16-byte base64 MD5, valid declared media type ≤128 chars; reject unknown keys. Both digests are computed client-side before issuance so the same request works with either pinned profile. Authenticate/enrollment/scope/rate-limit before R2 calls; accept no URL, key, owner or arbitrary headers.
2. In one SQLite transaction derive uploader, reserve bytes nonrefundably against the issue day's quota, allocate blob_id/key and store checksum profile/expected digest/deadlines. Return 201 `{blob_id,sha256,sha256_verified:false,integrity:{algorithm,value,verified:false},size,expires_at,upload:{method:"PUT",url,headers,expires_at},complete_url}`. Pending results never claim verification. Object expiry = grant issue +24h; PUT TTL = **5 min**. Same issuer/idempotency key/body returns the same ID/original deadlines; changed body is 409 `idempotency_conflict`; expired replay never silently issues a fresh grant. Regenerate a retry presign only within the original deadline; never extend it or persist URLs.
3. PUT exact bytes directly to R2 S3, no hub bearer/cookies, redirects disabled. SigV4 scope `<date>/auto/s3/aws4_request`, payload `UNSIGNED-PAYLOAD`. Sign `host`, exact `Content-Length`, `If-None-Match: *`, checksum header, `Content-Type: application/octet-stream`, `Content-Disposition: attachment` and `Cache-Control: private, no-store`. SHA profile uses base64 raw SHA in **signed header** `x-amz-checksum-sha256`; do not hoist it to a query parameter. MD5 profile uses base64 raw MD5 in signed `Content-MD5`. Sign persisted `x-amz-meta-vecnet-checksum-profile` and `x-amz-meta-vecnet-checksum` as well, for HEAD binding (metadata alone is never proof). Browser supplies Content-Length automatically from a fixed Blob; JS must not set that forbidden header. No chunked/multipart uploads.
4. `POST /v1/blobs/uploads/{blob_id}/complete`, bearer, empty JSON. Only issuer/principal or operator completes, with enabled credential recheck. Hub HEADs **its stored key** without receiving file bytes, checks exact length, signed stored metadata/disposition/cache policy, ETag and any provider checksum. Task 0 establishes the supported checksum evidence: prefer provider-returned SHA checksum; if unavailable, immutable existence plus matching signed checksum metadata is valid only because the spike proved no object can be created through that grant without R2 enforcing that checksum. MD5 profile must check the real-bucket-proven single-PUT MD5/ETag and size. A missing object is 409 `upload_incomplete`; leave reservation until deadline. Never accept a client PUT receipt, ETag or unsigned metadata as proof. A bucket write by privileged operator credentials is outside the grant threat model; isolate one hub's bucket and protect credentials.
5. CAS pending→complete in SQLite; record checksum profile, provider-verified digest+size, ETag and verification time, move reserved→accepted bytes once. For MD5 record `sha256_verified:false` permanently; no claimed SHA content addressing. Recheck expiry, issuer eligibility and purge tombstones after HEAD; network is outside transactions. Terminal mismatch rejects/enqueues deletion/charges failed usage. Attach only complete, authorized, unexpired, unpurged IDs in the send transaction. No Worker, verification GET or Fly hashing.

**Quota and replay:** Reserve at issue; do not refund abandoned/failed grants that day. Quota is `reserved + accepted + abandoned + rejected + new size <= daily_limit`; default 500 MiB/day permits twenty full 25 MiB grants including abandoned attempts. Issue day survives midnight/restart; idempotent calls never double-charge. Cap active grants 20/uploader and concurrent completion HEADs 2/hub, with 429 `upload_busy`/Retry-After. Conditional create-only PUT prevents replacement, but a deleted key can be recreated until the presign expires. Keep cleanup jobs through upload deadline+60s and re-delete then; tombstones prevent completion/attachment. These URLs are **as close to one-time upload as possible, not truly single-use**. Presign requests bypass hub rate limiting after issuance, so byte quotas and attempt limits do not bound all R2 replay request charges; monitor provider usage. True consume-once semantics need edge state and are outside the baseline.

### 3. Authorized signed GET, Range and safe rendering

`GET /v1/blobs/{sha256}/download?blob_id=<id>[&t=<token>]` returns `{method:"GET",url,expires_at,object_expires_at,blob_id,sha256,sha256_verified,integrity,size,media_type}` and `Cache-Control: no-store`. Accept existing bearer authorization or matching v2 delivery token; check enabled recipient, principal/history visibility, complete state, purge and `now < expires_at` before signing. Upload ownership alone does not grant read permission. Legacy `GET /v1/blobs/{sha256}?b=<id>&t=...` performs the same checks and returns a 307 to S3, never bytes. Disk/durable paths remain local; grant exchange returns `{local_path}` for them.

Issue method-bound S3 SigV4 **GET** for exactly the stored bucket/key on `https://<account>.r2.cloudflarestorage.com`, with `X-Amz-Expires = floor(min(120s, object_expires_at-now))`; decline if <1 second remains. **Two minutes is the shortest practical default** for host scheduling and up to 25 MiB transfers; never issue beyond the logical object deadline, and reacquire once if an unused URL expires. Sign exact response override parameters only where confirmed by Task 0/provider acceptance; baseline relies on immutable stored octet-stream/disposition/cache metadata. HEAD, PUT and DELETE require separate signatures; no arbitrary method/path/endpoint or client-selected response headers. Validate Range behavior (206/416, full/open/suffix, reject unsupported multi-range at the client), size bounds and Range CORS against S3. Clients do not treat partial ranges as full digest verification.

All clients use credential-free direct transport, fixed allowed endpoint from authenticated capabilities, no redirects, bounded streaming and no arbitrary `origin_url` fetch. Web fetches into a Blob then a download action with a sanitized local name; never inline SVG/HTML or untrusted images. R2 stores `application/octet-stream`, `Content-Disposition: attachment`, `Cache-Control: private, no-store`; original media type and filename are display metadata only, not trusted sniff results. Strip controls/bidi/path separators/CRLF, limit filename to 255 code points, use `textContent` for durable text. Verify actual final S3 response headers in acceptance.

**Baseline security limitation:** S3 cannot be assumed to support custom `X-Content-Type-Options`, CSP or Referrer-Policy response overrides. A hub redirect cannot add these to the final S3 response. We accept attachment-only stored metadata, client-controlled safe saving and no inline rendering in the no-Worker baseline; do not falsely promise those extra headers. Optional Task 10 adds them for custom-domain GETs without hashing.

Already-issued S3 GETs are replayable until their ≤120s deadline after recipient disable/token revocation. Purge deletes the object and prevents future grants, but is not instant individual-URL revocation. Treat expiration as a request-start boundary (include provider behavior in Task 0 acceptance); bytes already downloaded or a transfer begun before expiry cannot be clawed back. Hub logical expiry blocks new grants/references exactly at 24h; all preissued URLs are bounded by that deadline. Buckets have no public r2.dev or public custom-domain access. True single-use GETs need an edge component with atomic used-token state; a stateless optional Worker alone does not provide them.

### Security: ephemeral URLs in MCP model context

Max explicitly chooses URL-bearing MCP tool results. Treat each URL as a bearer capability: a model, transcript, MCP host telemetry or someone reading a retained tool result can replay/leak it within TTL. Assume the intended hosts can HTTP-transfer files and the upload/download domains are allowed; return URLs only on explicit authenticated blob transfer tool calls, never unsolicited inbox/history/resources/events or stored Message fields. Scope to one key, one method, exact upload length/checksum/conditional headers and the minimum practical TTL; issue neither bucket credentials nor list/delete capabilities. MCP hosts make requests themselves and omit hub auth/cookies. Do not offer a tool that fetches an arbitrary model-supplied URL through Fly.

Set `Cache-Control: no-store` on hub/MCP HTTP responses, mark URL fields sensitive in schemas/descriptions, redact all URL queries/signatures/credentials from server logs, traces, exceptions and audit details; usage records contain IDs/status/bytes only. Operator/host guidance disables tool-result/request-URL logging or redacts these fields where supported, and never pastes live URLs into tickets/chat. This cannot guarantee external transcript deletion: short TTL and narrow scope bound exposure. URLs must exist in the deliberate tool result; do not apply generic token-stripping there, while continuing to strip delivery tokens and URLs from every other MCP representation. No tool result claims either upload or download is truly single-use.

### 4. Expiry, metadata, durable text and avatars

Set R2 lifecycle `Expiration.Days=1` for `attachments/v1/` only. The hub denies new references/download grants at `issued_at+24h` even if the message is pinned; every S3 GET presign is bounded by that deadline (with request-start/in-flight limitations above). Do not set HTTP `Expires` and call that deletion. A 30-second ticker marks expired objects, enqueues deletion, and retries with bounded exponential backoff. Lifecycle provides disaster cleanup if the hub is down; physical deletion has no exact 24-hour SLA. UI calls this **“Attachment expired (24-hour retention)”**, not “physically deleted at 24 hours.”

Authorized HTTP reads/completions/references after expiry return **410 `blob_expired`**, distinct from 410 `blob_purged`; incomplete is 409 `upload_incomplete`; unknown/unowned sends keep generic 422 `unknown_blob`. Download grants after provider loss before expiry return 503 `blob_unavailable` (retryable), not a false expiry. Direct S3 errors are mapped by clients to sanitized `blob_unavailable` or expired-capability status; reconcile with the hub once for authoritative expiry/purge and never print raw URLs/XML. Expired S3 URL while the object is live: reacquire once. Expired/purged objects never fall back automatically to `origin_url`.

Add an additive `blob_states` projection to authorized history/inbox/HTTP/MCP representations, keyed by blob_id and containing `{state:"available"|"expired"|"purged"|"unavailable",expires_at}`; no credentials or URLs in MCP projections; explicit transfer tool results alone carry URLs. Include checksum trust fields so fallback SHA is never presented as verified. Disk hash entries retain existing `hosted_blobs` semantics. Project from the clock even before the ticker runs. Keep attachment name/size/hash/ID in retained messages. Web files panel and message chips show the exact expired label and disable download; TUI shows `[attachment expired: <name>]` and keeps preview text; CLI human output prints that label, JSON retains reference plus projection, and `blob get` exits 1 with machine-readable `blob_expired`; MCP `isError` includes code `blob_expired` and no data. Refresh open web/TUI rows on a timer at expires_at and on a 410. Distinguish expired from purged in existing UI logic that currently treats every 410 as purge.

For R2 mode auto-spills, persist full text once in SQLite `durable_blob_payloads` (sha, purpose=`spill`, media_type, bytes, created_at), with existing message references and preview/`vecnet.spilled` semantics. Maximum is the existing 65,536 UTF-8 bytes/send. Keep full text outside duplicated event JSON. `applySpill`/`putSpill` must dispatch to this durable path, never a presigned upload or the external attachment quota. Preserve a separate hub text quota and current error mapping. Legacy tokenized spill URL, TUI/web text expansion and MCP base64 spill reads resolve the database payload through the existing access rules and remain usable after 24 hours. Local mode continues its current disk spill behavior.

Source raw JSON is also hub-authored message data, not a client file transfer: in R2 mode `IngestSource` stores it in the same durable table with purpose=`source_raw`, bounded by the existing source ingress cap and source daily quota; external source adapters use the ordinary direct upload protocol for actual files. Keep provenance/purpose and authorization separate so an attachment with a matching hash cannot promote an expiring upload into durable storage. Avatar PNG table, 2 MiB input cap, normalization, read rules and deletion on last peer reference stay unchanged. Message/avatar API bodies and durable text reads still use Fly; document these explicit content paths, and do not describe the system as zero-byte Fly traffic.

### 5. Tables, purge, GC and migration

One additive migration (next free number at build time) introduces:

- `blob_objects`: blob_id PK; sha256; backend=`r2`; random object_key UNIQUE; uploader; size; declared media_type; content_md5; issued_at; upload_deadline; expires_at; checksum_profile; expected_checksum; state pending/complete/rejected/abandoned/expired/purged; sha256_verified (false for MD5); verified_algorithm/verified_digest/verified_size/etag/verified_at; purged_at; deletion_confirmed_at. Constraints on states/size/hash and indexes on uploader+state and state+expiry.
- `blob_upload_requests`: uploader+idempotency_key PK, canonical request digest, blob_id, issue_day. No signed URL column. Keep request records seven days; return 410 `upload_grant_expired` for expired replay within that window. Clients use a fresh key to start again intentionally.
- `blob_object_refs`: msg_id+blob_id PK, sha256, with FK to messages and objects. Update `checkAttachments`, transaction pinning, visibility queries, history projection and delivery decoration to consult these rows as well as existing disk `blob_refs`/`blob_uploaders`.
- `blob_r2_quota`: uploader+UTC day PK; reserved_bytes, accepted_bytes, abandoned_bytes, rejected_bytes (all nonnegative). Their sum enforces the daily limit; CAS transitions move, never duplicate amounts. Keep ordinary disk `blob_quota` unchanged. On cutover seed the R2 current-day usage from disk quota so switching does not reset a user's limit; rollback must account for that day's remote reservations too.
- `durable_blob_payloads`: sha256+purpose PK, bytes, media_type, created_at; `durable_blob_refs`: msg_id+sha256+purpose PK. Old disk spill references keep their grandfathered location; no migration task or byte movement at startup.
- `blob_purge_tombstones`: sha256 PK, purged_at, actor (permanent for existing purge semantics); `blob_delete_jobs`: object key PK, blob_id, not_before, attempts, next_attempt, last sanitized code. Purging a hash affects every R2 incarnation plus existing disk/durable objects and future completion, preserving hash-level prohibition on re-upload. Do not disclose tombstones to unrelated callers; an authorized uploader completing the enforced checksum path can receive `blob_purged`. In MD5 mode a declared SHA is not proof of actual SHA; hash purge cannot detect a dishonest new SHA claim. Preserve this explicit limitation rather than claim verified hash-wide suppression.
- `blob_usage_events`: event_id PK, blob_id/uploader/day, kind, byte_count, at. Transactionally record reserve/verified/rejected/abandoned/expired/delete_confirmed once per transition; do not invent SaaS tenant IDs from principals.

Keep expired object stubs while any retained message refers to them. They explain a persistent 410 and protect against resurrection. Drop unreferenced expired/rejected/abandoned rows, uploader associations and idempotency entries after seven days **and** confirmed deletion **and** upload deadline+60s; retain hash purge tombstones indefinitely. Keep quota counters 35 days; retain metering ledger 90 days with an explicit future billing-export retention decision. Reconcile delete jobs after restart.
