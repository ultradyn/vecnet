# R2 Blobs with Direct Transfers and 24-Hour Expiry Implementation Plan

> **For agentic workers:** Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement task by task. Follow the house task/review gates in `docs/plans/2026-11-05-hub-notices.md`. Steps use checkbox (`- [ ]`) syntax. A `---` ends every task. This document is a plan; its creation does not authorize deployment or resource creation.

**Goal:** Fly-hosted hubs authorize private, signed attachment transfers whose file bytes never traverse Fly, with exactly 24 hours of application availability, while local hubs retain their existing disk backend.

**Architecture:** Keep authorization, reservations, object state and message references in SQLite. Clients PUT directly to R2 using a tiny stdlib SigV4 presigner. A small Cloudflare Worker with a private R2 binding verifies uploaded SHA-256 values and streams downloads through hub-signed, two-minute GET capabilities; this is necessary to verify the actual SHA-256 without reading bytes on Fly and to guarantee download security headers. The Worker is part of the R2 backend, not an optional hardening add-on. Persistent message text and avatars remain database content, outside attachment expiry.

**Tech Stack:** Existing Go toolchain, `CGO_ENABLED=0`, Go stdlib `crypto/hmac`, `crypto/sha256`, `crypto/md5` (transfer checksum only), `encoding/xml`, `net/http`; vanilla browser modules; Node connector code; one TypeScript Cloudflare Worker using R2 bindings, Web Crypto HMAC and `crypto.DigestStream`. No AWS SDK or new Go module. Pin Worker dev tooling in its own lockfile; never import it into the hub or CLI.

## Current behavior and implications

- `internal/blob/store.go` streams to disk, hashes, dedupes globally, charges 25 MiB/file and 500 MiB/uploader/UTC day defaults, and records all uploaders. Its GC removes only **unreferenced** bytes; pins override TTL. Neither that TTL nor the seven-day HMAC read-token lifetime implements this requirement.
- `internal/httpapi/blobs.go` currently receives PUT bodies and serves seekable GETs with Range, `nosniff` and CSP sandbox. `internal/hub/blobs.go` authorizes a recipient token (including an enabled-peer check), operator, or history-visible thread participant. `checkAttachments` in `internal/hub/spill.go` prevents hash guessing from granting attachment access.
- `spill.go` stores full long text as a blob uploaded by `hub`, then emits a preview and `message.md`. `internal/hub/sources.go:IngestSource` also stores source raw JSON as an attachment. Both need an explicit durable message-data path before R2 is enabled.
- Contrary to the assignment's premise about avatars, `internal/hub/avatar.go` already normalizes images and stores PNG bytes in `avatars.png` in SQLite (migration `0016_peer_avatars.sql`). Preserve that behavior; do not migrate avatars to expiring storage.
- CLI `app.upload` in `internal/cli/commands.go`, `internal/opclient.Client.Upload/Blob` (also used by the TUI), web `api.js`, and connector `HubApi.putBlob/fetchBlob` are separate transfer entry points. There is currently no top-level `vecnet blob get` command; add it rather than referring users to a nonexistent command.
- MCP currently accepts 160 KiB decoded PUTs and returns 128 KiB base64 GET pages, deliberately stripping delivery read tokens. Maintaining those byte paths for remote attachments would violate the Fly constraint even at their present small caps.

| Contract | Evidence and decision |
|---|---|
| Presigning | [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/r2/api/s3/presigned-urls.mdx): PUT/GET/HEAD/DELETE; expiry 1 second–7 days; HTML form POST is unsupported; signed Content-Type must match. Use PUT. S3 presigns only work on the R2 S3 domain, not custom public domains. |
| Upload checksum | [S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/r2/api/s3/api.mdx): PutObject explicitly supports `Content-MD5`. The checksum table lists SHA-256 as COMPOSITE, not FULL_OBJECT; it does not establish that a single-PUT `x-amz-checksum-sha256` can provide our full-object SHA-256 proof. Select signed **Content-MD5**, base64 of the 16 raw MD5 bytes, and independently compute SHA-256 in the Worker. Never equate MD5, ETag, or client-supplied metadata with verified SHA-256. |
| Immutable upload | [R2 extensions](https://developers.cloudflare.com/r2/api/s3/extensions/), [source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/r2/api/s3/extensions.mdx): `If-None-Match: *` on PUT atomically permits at most one writer. Sign this header; an existing key returns 412. |
| Physical expiry | [Object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/), [source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/r2/buckets/object-lifecycles.mdx): deletion typically occurs within 24 hours **after** `x-amz-expiration`, and migration of existing objects to rules may take longer. A one-day rule is a cleanup backstop, not an exact deletion deadline. |
| Browser CORS | [R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/), [source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/r2/buckets/cors.mdx): browser presigns still need bucket CORS; explicit origins/headers/methods and exposed response headers. |
| Streaming verification | [Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/), [source](https://github.com/cloudflare/cloudflare-docs/blob/production/src/content/docs/workers/runtime-apis/web-crypto.mdx): `crypto.DigestStream("SHA-256")` hashes without retaining bytes. Use it while counting the uploaded object stream. |

**Why the Worker:** Direct R2 S3 GET cannot be assumed to support an arbitrary `X-Content-Type-Options` response override; hub redirect headers do not protect the final response. A private edge GET signer and R2 binding let us set `nosniff`, CSP and disposition ourselves. This deliberately chooses a **hub-presigned edge GET**, not an S3-presigned GET, and adds one Worker verification read plus Worker download requests. File bytes flow client→R2, R2→Worker for verification, and R2→Worker→reader. There is no Fly data proxy. The implementation must include Worker operating/request costs in the pricing analysis; this plan does not claim a zero-cost edge path.

## Global Constraints

- Plan only here. During implementation, no cloud resource creation, secrets changes, deploy or real-R2 tests without separate operator authorization. Never print secrets or complete signed URLs. No `attn`.
- Disk is the default. R2 selection is explicit and invalid R2 config fails startup; never silently fall back to disk during an outage. Disk PUT/GET, TTL, dedupe, tokens, pinning and GC remain compatible.

- Message text (including auto-spills and source webhook message-data) and avatar PNGs are explicit database-content exceptions: they already enter the hub as message/avatar API data, are never relayed to R2, and do not expire at 24 hours. This is not a proxy for arbitrary file attachments.

No outbound network in automated tests; in-process HTTP servers and local Worker runtime only. Never read/write the real config, `.data/`, `.demo-data/`, dev hub 45752 or preview 49575.

## Decisions and wire contracts

### 1. Isolated objects, content hashes and attachment identity

Keep SHA-256 as the integrity/content address. Add optional `blob_id` to the attachment schema and require it for new R2-hosted uploads. IDs are server-generated `blo_` plus a 26-character Crockford base32 encoding of 128 cryptographically random bits (first character 0–7). Use a separate random-ID mint, not the monotonic timestamp ULID generator; register the prefix and validate the same 26-character shape. IDs are unguessable but still confer no authority. An upload result is `{blob_id,sha256,size,expires_at}`. The client includes `blob_id` when sending; the hub validates ownership/visibility and exact sha/size before pinning. Disk and old messages omit it.

An R2 physical object has key `attachments/v1/<hub_namespace>/<blob_id>`; no uploader IDs, filenames or user-controlled paths. Namespace is random and persisted in SQLite at setup. Do **not** physically dedupe R2 uploads across uploaders or retention generations in this release: global sharing exposes existence/timing and entangles independent 24-hour lifetimes. Identical bytes still have identical SHA-256, but get isolated keys and IDs; charge each grant's size. Do not return “already exists” or skip the PUT based on a global hash query. Disk dedupe is unchanged. This is a deliberate tradeoff for ephemeral storage, not a promise of cross-uploader storage savings.

Re-upload after expiry creates a new blob_id and lifetime. An old message continues naming the old ID and stays expired; a new upload cannot resurrect it. Hash-only R2 requests are rejected with 422 `blob_id_required`, after normal caller authentication, rather than selecting the newest incarnation. Legacy hash-only requests still resolve disk or durable message-data objects. Bind new HMAC delivery tokens to `(recipient, sha256, blob_id)` with a versioned format; continue validating v1 hash-only disk tokens. Never allow a v1 token to access any R2 incarnation.

### 2. Upload grant → immutable PUT → verification → attach

1. `POST /v1/blobs/uploads` with bearer, `Idempotency-Key`, and JSON `{size,sha256,content_md5,media_type}`. Require integer size 1..25 MiB, 64 lower-case SHA hex, canonical 16-byte MD5 base64, valid media type ≤128 chars. Reject unknown keys. Authenticate/enrollment/scope and rate-limit before any R2 call. No URL, object key, owner or custom headers are accepted from clients.
2. In one SQLite write transaction derive uploader, check enabled state and limits, allocate ID/key and charge a nonrefundable byte reservation to the issue day's quota. `used_bytes + reserved_bytes + size <= daily_limit`. Return 201 `{blob_id,sha256,size,expires_at,upload:{method:"PUT",url,headers,expires_at},complete_url}`. Attachment expiry is **grant issue time +24h**, upload URL TTL **5 min**. An idempotent retry of the same issuer/key/body returns the same ID and original deadline; changed body is 409 `idempotency_conflict`; an expired key does not create an unnoticed new grant. No presign appears in durable audit records.
3. Client PUTs the exact body directly to the configured R2 S3 endpoint, with no hub bearer/cookies and redirects disabled. SigV4 scope is `<date>/auto/s3/aws4_request`; canonical payload is `UNSIGNED-PAYLOAD`, with `Content-MD5`, `Content-Length`, `Content-Type`, `If-None-Match: *`, `Cache-Control: no-store` and `Content-Disposition: attachment` all signed as headers. `host` is signed too. Browser sets Content-Length itself from a fixed Blob; JS must not try to set that forbidden header. Its value is still part of the signature. No chunked/multipart uploads. MD5 detects transfer corruption; it is not the SHA-256 security proof.
4. `POST /v1/blobs/uploads/{blob_id}/complete` with bearer and empty JSON. Only the original uploader/principal or operator can complete; recheck enabled credential. Hub performs authenticated HEAD on **its stored key**, checks Content-Length, content type, metadata/disposition and ETag, then asks the Worker to verify that same key. A missing object is 409 `upload_incomplete`; keep the reservation/grant until deadline. Never trust a client-provided receipt, ETag or `x-amz-meta-sha256`.
5. Hub→Worker control request `POST /internal/verify` is a 60-second HMAC-authenticated JSON request binding hub namespace, blob_id, expected size/SHA, observed ETag and random nonce. Worker reads only the derived key from its R2 binding, checks ETag, streams to a counter and SHA-256 DigestStream, cancels at size+1 or 25 MiB+1, and compares hash/length. Return HMAC-authenticated JSON `{blob_id,sha256,size,etag,nonce,verified_at}`; timestamp skew ≤30s and nonce must match the pending request. Canonical control signing bytes are `vecnet-r2-verify-request-v1\n` followed by a JSON array `[1,hub_namespace,blob_id,size,sha256,etag,nonce,exp]`; exp is integer UTC seconds. Response signing bytes use `vecnet-r2-verify-response-v1\n` plus `[1,hub_namespace,blob_id,size,sha256,etag,nonce,verified_at,result]`, where result is `verified` or `mismatch`. JSON has no whitespace, lowercase SHA hex and base64url nonce; both implementations share literal byte vectors. The shared key is separate from blob tokens. The hub authenticates the response and validates every bound field. Worker accepts no arbitrary fetch URL or bucket name.
6. A transaction CASes pending→complete, stores verified proof, and moves reserved→accepted bytes (never adding a second quota charge). Recheck issue/expiry, uploader eligibility and hash purge tombstone after the network work. Network I/O is outside SQLite transactions. Concurrent completion is idempotent. Failure/mismatch is terminal rejected, enqueues delete, and records failed-reservation usage. Sending references a **complete, unexpired, unpurged** authorized object within the send transaction. No attach-then-verify window.

**Quota and replay:** Reserve at issue and do not refund abandoned/failed grants for that UTC day. A 500 MiB limit allows at most twenty full 25 MiB grants/day, including abandoned ones. This bounds untrusted attempts without refund/HEAD races; document this conservative change for R2. Same idempotency key never reserves twice. Before midnight grants remain charged to the issue day after midnight. Expired pending reservations move to `abandoned_bytes`, still counted against that day's 500 MiB until natural day rollover. Cap active grants at 20/uploader and verification concurrency at 2/hub and 2/Worker instance, returning 429 `upload_busy` with Retry-After. Sign `If-None-Match: *` so a replay cannot replace completed bytes. After delete, the signed PUT might recreate the key until its five-minute expiry: retain cleanup jobs and retry after upload deadline plus a 60-second grace. Tombstones and grant state prevent completion during that window. R2 cannot make a presign single-use; never describe it as such. Attempt rate limits bound replay request costs, not just quota bytes.

### 3. Authorized signed GET, Range and safe rendering

`GET /v1/blobs/{sha256}/download?blob_id=<id>[&t=<token>]` returns JSON `{url,expires_at,object_expires_at,blob_id,sha256,size,media_type}` with `Cache-Control: no-store`. Accept either existing bearer rules or the matching v2 delivery token. Before signing, check recipient still enabled, principal ownership/history visibility, complete state, purge and `now < expires_at`. Do not grant uploader read access merely because it uploaded: preserve current participant/operator read policy. Legacy `GET /v1/blobs/{sha256}?b=<id>&t=...` performs the same checks and returns a 307 to the edge URL, never bytes. Disk/durable message-data responses remain local; the explicit grant endpoint returns `{local_path}` for those instead of an edge URL.

The edge GET capability is query fields `v=1,kid,hub,blob_id,sha256,size,etag,object_expires_at,exp,disposition,filename` and `sig`. Sign a canonical JSON array of those fields in that order, UTF-8 bytes, domain separator `vecnet-r2-download-v1\n`, HMAC-SHA256, base64url without padding. Integers must be canonical decimal safe integers, no duplicate query keys, unknown fields, controls or encoded separators. `exp = min(now+120s, object_expires_at)` in UTC seconds; decline if less than one second remains. Keys never appear in the URL. Use separate keys/domain separators for verify requests, verify responses and downloads, with current+previous key IDs for a bounded rotation overlap.

Worker verifies signature in constant-time, deadline and object deadline on every GET, derives key from configured namespace+ID, compares stored ETag/size, and uses private R2 binding GET. It does not follow redirects or accept arbitrary origins/URLs. Single `Range: bytes=start-end`, open-ended or suffix range is allowed; implement 206, Accept-Ranges, Content-Range and 416 with explicit bounds. Reject multi-range, malformed and overflow values. A range is bounded to the same signed object, so need not be fixed in the signature. HEAD uses a separately signed method capability if added; a GET signature must not authorize DELETE, PUT, verification or other paths. Do not sign raw request target strings whose percent-encoding is ambiguous.

Serve **all first-release downloads** as `application/octet-stream`, `Content-Disposition: attachment; filename="attachment"; filename*=UTF-8''<sanitized-name>`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'`, `Cache-Control: private, no-store`, and `Referrer-Policy: no-referrer`. Filename is only display metadata, limited to 255 code points, stripped of controls/bidi/path separators and CR/LF, and RFC 5987 encoded. The original media type remains metadata; it is not a trusted sniff result. This meets the non-image download rule conservatively by forcing image downloads too; no SVG/HTML inline previews. Future image previews require edge decoding/type validation, not extension/header trust. Web uses fetch→Blob→download attribute, and uses `textContent` only for durable message text. Edge CORS permits exact UI origin, GET/HEAD and Range only, without credentials. No edge/CDN caching of private bodies.

Already-issued edge capabilities remain valid for at most 120 seconds after recipient disable/token revocation; no new ones issue. Purge deletes the object (edge reads immediately fail once deletion completes) and revokes all future grants. Request-start checks cannot claw back bytes already downloaded or abort every transfer that crosses the deadline. Record this bounded revocation limitation in PROTOCOL, not as an open security promise. The bucket has no public custom domain or r2.dev endpoint.

### 4. Expiry, metadata, durable text and avatars

Set R2 lifecycle `Expiration.Days=1` for `attachments/v1/` only. The hub denies new references/download grants at `issued_at+24h` even if the message is pinned; the Worker independently enforces that deadline. Do not set HTTP `Expires` and call that deletion. A 30-second ticker marks expired objects, enqueues deletion, and retries with bounded exponential backoff. Lifecycle provides disaster cleanup if hub/Worker are down; physical deletion has no exact 24-hour SLA. UI calls this **“Attachment expired (24-hour retention)”**, not “physically deleted at 24 hours.”

Authorized HTTP reads/completions/references after expiry return **410 `blob_expired`**, distinct from 410 `blob_purged`; incomplete is 409 `upload_incomplete`; unknown/unowned sends keep generic 422 `unknown_blob`. Download grants after provider loss before expiry return 503 `blob_unavailable` (retryable), not a false expiry. Edge object missing responses use a sanitized 404 `blob_unavailable`; clients reconcile with hub once for authoritative expiry/purge and do not retry forever. Expired edge URL while object still live: reacquire once. Expired/purged objects never fall back automatically to `origin_url`.

Add an additive `blob_states` projection to authorized history/inbox/HTTP/MCP representations, keyed by blob_id and containing `{state:"available"|"expired"|"purged"|"unavailable",expires_at}`; no credentials or URLs in MCP projections. Disk hash entries retain existing `hosted_blobs` semantics. Project from the clock even before the ticker runs. Keep attachment name/size/hash/ID in retained messages. Web files panel and message chips show the exact expired label and disable download; TUI shows `[attachment expired: <name>]` and keeps preview text; CLI human output prints that label, JSON retains reference plus projection, and `blob get` exits 1 with machine-readable `blob_expired`; MCP `isError` includes code `blob_expired` and no data. Refresh open web/TUI rows on a timer at expires_at and on a 410. Distinguish expired from purged in existing UI logic that currently treats every 410 as purge.

For R2 mode auto-spills, persist full text once in SQLite `durable_blob_payloads` (sha, purpose=`spill`, media_type, bytes, created_at), with existing message references and preview/`vecnet.spilled` semantics. Maximum is the existing 65,536 UTF-8 bytes/send. Keep full text outside duplicated event JSON. `applySpill`/`putSpill` must dispatch to this durable path, never a presigned upload or the external attachment quota. Preserve a separate hub text quota and current error mapping. Legacy tokenized spill URL, TUI/web text expansion and MCP base64 spill reads resolve the database payload through the existing access rules and remain usable after 24 hours. Local mode continues its current disk spill behavior.

Source raw JSON is also hub-authored message data, not a client file transfer: in R2 mode `IngestSource` stores it in the same durable table with purpose=`source_raw`, bounded by the existing source ingress cap and source daily quota; external source adapters use the ordinary direct upload protocol for actual files. Keep provenance/purpose and authorization separate so an attachment with a matching hash cannot promote an expiring upload into durable storage. Avatar PNG table, 2 MiB input cap, normalization, read rules and deletion on last peer reference stay unchanged. Message/avatar API bodies and durable text reads still use Fly; document these explicit content paths, and do not describe the system as zero-byte Fly traffic.

### 5. Tables, purge, GC and migration

One additive migration (next free number at build time) introduces:

- `blob_objects`: blob_id PK; sha256; backend=`r2`; random object_key UNIQUE; uploader; size; declared media_type; content_md5; issued_at; upload_deadline; expires_at; state pending/complete/rejected/abandoned/expired/purged; verified_sha256/etag/verified_at; purged_at; deletion_confirmed_at. Constraints on states/size/hash and indexes on uploader+state and state+expiry.
- `blob_upload_requests`: uploader+idempotency_key PK, canonical request digest, blob_id, issue_day. No signed URL column. Keep request records seven days; return 410 `upload_grant_expired` for expired replay within that window. Clients use a fresh key to start again intentionally.
- `blob_object_refs`: msg_id+blob_id PK, sha256, with FK to messages and objects. Update `checkAttachments`, transaction pinning, visibility queries, history projection and delivery decoration to consult these rows as well as existing disk `blob_refs`/`blob_uploaders`.
- `blob_r2_quota`: uploader+UTC day PK; reserved_bytes, accepted_bytes, abandoned_bytes, rejected_bytes (all nonnegative). Their sum enforces the daily limit; CAS transitions move, never duplicate amounts. Keep ordinary disk `blob_quota` unchanged. On cutover seed the R2 current-day usage from disk quota so switching does not reset a user's limit; rollback must account for that day's remote reservations too.
- `durable_blob_payloads`: sha256+purpose PK, bytes, media_type, created_at; `durable_blob_refs`: msg_id+sha256+purpose PK. Old disk spill references keep their location until an explicit local operator migration; no automatic byte movement at startup.
- `blob_purge_tombstones`: sha256 PK, purged_at, actor (permanent for existing purge semantics); `blob_delete_jobs`: object key PK, blob_id, not_before, attempts, next_attempt, last sanitized code. Purging a hash affects every R2 incarnation plus existing disk/durable objects and future completion, preserving hash-level prohibition on re-upload. Do not disclose tombstones to unrelated callers; an uploader proving those bytes by completed verification can receive `blob_purged`.
- `blob_usage_events`: event_id PK, blob_id/uploader/day, kind, byte_count, at. Transactionally record reserve/verified/rejected/abandoned/expired/delete_confirmed once per transition; do not invent SaaS tenant IDs from principals.

Keep expired object stubs while any retained message refers to them. They explain a persistent 410 and protect against resurrection. Drop unreferenced expired/rejected/abandoned rows, uploader associations and idempotency entries after seven days **and** confirmed deletion **and** upload deadline+60s; retain hash purge tombstones indefinitely. Keep quota counters 35 days; retain metering ledger 90 days with an explicit future billing-export retention decision. Reconcile delete jobs after restart. GC durable payloads only after their last retained message reference disappears; no time expiry. Meter DB occupancy separately from R2.

**Existing Fly disk blobs:** no bulk copy or hub→R2 forwarding. Inventory counts/bytes by purpose and references without logging names/content. On R2 enable, leave referenced local attachments and spills on disk; serve their existing paths and retention semantics as a clearly documented grandfathered exception. Ordinary unreferenced uploads already expire by old GC. They cannot all be “left to expire” because pins currently keep them forever. New uploads all use R2; show backend/retention in operator metadata. Do not destroy grandfathered bytes or reset pins to force the new policy. If strict zero-file-byte Fly service is required at cutover, a separate authorized **operator-side** downloader/uploader must migrate or retire those objects before switching; that is not this release's automatic migration. Rollback to disk preserves R2 metadata/reads until their 24-hour window ends, while only new uploads switch; never pretend remote objects are disk paths. Both choices are explicit exceptions to the new-upload contract, not hidden fallbacks.

## Operator setup runbook (Max, after implementation)

1. **Prepare:** choose one bucket and one Worker per hosted hub, record account/jurisdiction, hub namespace, exact UI origin and edge origin. Keep disk default until compatible clients are installed. Inventory existing Fly disk references; choose the documented grandfathering path or separately authorize operator-side migration/retirement for a strict cutover.
2. **Create private storage:** create a Standard R2 bucket. Disable public `r2.dev` and public custom-domain access. Do not use infrequent-access storage for one-day objects. Do not create a bucket automatically from runtime requests.
3. **Set lifecycle** on the prefix, using the R2 dashboard or operator S3 lifecycle tool; runtime credentials do not set it:

   ```json
   {"Rules":[{"ID":"vecnet-attachments-one-day","Status":"Enabled","Filter":{"Prefix":"attachments/v1/"},"Expiration":{"Days":1}}]}
   ```

   Read it back and record the rule, understanding deletion lag. The Worker never serves expired capabilities even while objects await lifecycle deletion.
4. **Set bucket CORS**, exact production UI origin only (add development origins only on a separate development bucket):

   ```json
   [{"AllowedOrigins":["https://vecnet.xk.io"],"AllowedMethods":["PUT","HEAD"],"AllowedHeaders":["content-type","content-md5","content-length","if-none-match","cache-control","content-disposition"],"ExposeHeaders":["ETag","Content-Length"],"MaxAgeSeconds":300}]
   ```

   Browser sets Content-Length automatically; include it in signature validation, not a JS setRequestHeader call. Worker download CORS separately allows that exact origin, GET/HEAD, Range and exposed Content-Range/Accept-Ranges/Content-Length/ETag; it never allows credentialed cross-origin requests or wildcard origin.
5. **Create least-privilege R2 API credential:** Object Read & Write on this bucket only. Store access key ID and secret in a password manager. The Worker uses its one-bucket R2 binding and does not receive the S3 secret. Keep bucket admin credentials out of Fly.
6. **Deploy Worker:** bind the private bucket, hub namespace and UI origin, install a fresh shared edge key using the provider secret-input facility, and record its HTTPS origin/key ID. Use separate HMAC domain separators; restrict control request payload sizes, verification concurrency and request limits. Disable request-URL/query logging and caches. This resource creation/deployment is an operator step, not performed by this planning task.
7. **Set Fly secrets:** import `VECNET_R2_ACCESS_KEY_ID`, `VECNET_R2_SECRET_ACCESS_KEY`, `VECNET_BLOB_EDGE_KEY` using `fly secrets import -a vecnet` from a private temporary env file or secure stdin. Do not put literal values in shell history, command arguments, tracked files or chat. Set nonsecrets backend/account/bucket/endpoint/edge URL/key ID/lifecycle days in deployment configuration; keep `VECNET_PUBLIC_URL` unchanged. Inspect only secret names/status afterward.
8. **Acceptance before enabling R2:** with explicitly authorized disposable fixtures, verify browser+CLI 1 byte/25 MiB PUT, exact length mismatch, wrong Content-MD5 rejection, missing/changed signed headers, conditional replay 412, Worker SHA mismatch, successful complete/send, no-bearer download, 206/416, headers/CORS, disable/purge, and logical expiry with a test clock. Check Worker and R2 metrics; confirm no Fly file-byte transfer. Do not call fake-server success proof of provider compatibility. If exact signed Content-Length or If-None-Match fails on the real provider/browser, stop enablement and repair the design; never silently drop those bindings.
9. **Enable and observe:** enable R2 only after all clients and Worker are ready. Watch pending/abandoned quotas, verification latency, R2/Worker requests, expired/delete backlog and occupied bytes; no signed URLs or secrets in logs. Run a real one-day fixture to observe metadata expiry and eventual physical deletion separately. Backup SQLite, including namespace/ref/tombstone state; DB restore alone does not restore expired R2 objects. Rollback changes only new uploads to disk and continues remote reads/cleanup until remote lifetimes end.

## Remaining product decisions and release gates

- **MCP-only clients lose ordinary file put/get on R2.** This is the explicit consequence of the zero-byte Fly requirement. A host-side transfer integration is future work; the implementation may ship the documented limitation without inventing a proxy exception.
- **Worker operating scope:** this plan selects the Worker as required for safe downloads and SHA proof. Max still needs to choose account/region/bucket name, Worker limits and budget when authorizing resources. If Worker deployment is unacceptable, revisit the architecture before implementation; a metadata-only HEAD does not solve hash proof or final-response headers.
- **Existing pinned disk files:** the default is grandfathering, with clearly reported residual Fly file traffic. A strict cutover requires separately authorized operator-side migration/retirement; no data-destructive expiry conversion is assumed.
- **Physical deletion deadline:** logical availability is exactly 24h; lifecycle and retries are eventual cleanup. If the requirement expands to guaranteed physical destruction at exactly 24h, R2 lifecycle alone cannot promise that and this design needs a different deletion contract.
- **Billing:** usage hooks are included; account mapping, edge metric export/reconciliation and retention/legal policy must be decided before charging measured downloads. No pricing model is selected by this plan.

--- SUMMARY ---

- Optional disk/R2 configuration; new R2 file bytes use direct signed PUTs and signed edge GETs, with no Fly proxy and a hosted MCP proxy cap of 0 bytes.
- Signed exact length and Content-MD5, atomic create-only keys, Worker streaming SHA-256 proof and transactional completion prevent unverified attachments and grant-replay replacement.
- Daily quotas reserve at grant creation, survive crashes/midnight and charge abandoned attempts; per-incarnation IDs isolate uploaders and prevent old references from reviving.
- 24-hour metadata/edge denial overrides message pins; one-day R2 lifecycle plus deletion jobs cleans bytes eventually. Every client keeps expired references and reports `blob_expired` distinctly from purge.
- Long message spills and source raw message-data remain durable SQLite content; avatars already live there. Local-disk semantics remain intact, and existing pinned Fly files are explicitly grandfathered unless an operator migration is authorized.
- Nine tasks cover signer/schema, edge, reservation/durable content, hub API/config, state/metering, CLI/TUI, web, MCP/connectors and protocol/runbook; tests use local fakes and build-box gates, never real R2 by default.
- Open questions/release gates: operator Worker budget/location, acceptance of MCP-only file limits, strict migration versus grandfathering, physical-deletion expectations and future download billing reconciliation. No cloud resources, deployment or implementation is part of this planning assignment.
