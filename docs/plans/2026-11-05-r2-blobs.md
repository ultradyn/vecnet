## Current behavior and implications

- `internal/blob/store.go` streams to disk, hashes, dedupes globally, charges 25 MiB/file and 500 MiB/uploader/UTC day defaults, and records all uploaders. Its GC removes only **unreferenced** bytes; pins override TTL. Neither that TTL nor the seven-day HMAC read-token lifetime implements this requirement.
- `internal/httpapi/blobs.go` currently receives PUT bodies and serves seekable GETs with Range, `nosniff` and CSP sandbox. `internal/hub/blobs.go` authorizes a recipient token (including an enabled-peer check), operator, or history-visible thread participant. `checkAttachments` in `internal/hub/spill.go` prevents hash guessing from granting attachment access.
- `spill.go` stores full long text as a blob uploaded by `hub`, then emits a preview and `message.md`. `internal/hub/sources.go:IngestSource` also stores source raw JSON as an attachment. Both need an explicit durable message-data path before R2 is enabled.
- Contrary to the assignment's premise about avatars, `internal/hub/avatar.go` already normalizes images and stores PNG bytes in `avatars.png` in SQLite (migration `0016_peer_avatars.sql`). Preserve that behavior; do not migrate avatars to expiring storage.
- CLI `app.upload` in `internal/cli/commands.go`, `internal/opclient.Client.Upload/Blob` (also used by the TUI), web `api.js`, and connector `HubApi.putBlob/fetchBlob` are separate transfer entry points. There is currently no top-level `vecnet blob get` command; add it rather than referring users to a nonexistent command.
- MCP currently accepts 160 KiB decoded PUTs and returns 128 KiB base64 GET pages, deliberately stripping delivery read tokens. Maintaining those byte paths for remote attachments would violate the Fly constraint even at their present small caps.

## Decisions and wire contracts

### 1. Isolated objects, checksums and attachment identity

Add optional `blob_id` to the attachment schema and require it for new R2 uploads. IDs are server-generated `blo_` plus a 26-character Crockford base32 encoding of 128 cryptographically random bits (first character 0–7). Use a random-ID mint rather than timestamp ULIDs. IDs confer no authority. Each grant allocates one key `attachments/v1/exp/<class>/<hub_namespace>/<blob_id>` or `attachments/v1/keep/<hub_namespace>/<blob_id>` for `off`; the namespace is random and persisted in SQLite. Class-first prefixes require exactly six object-expiration rules across any number of pooled hubs, avoiding the R2 per-bucket rule cap; keep is outside every expiring prefix. Keys contain no filenames, uploader IDs or client paths. **The key is the grant ID, never a content hash**, with selected profile `sha256`. No cross-uploader or cross-generation dedupe: independent grant-time retention and small files make dedupe savings minor, while isolation avoids existence leaks and retention coupling. Disk dedupe remains unchanged.

Checksum profile `sha256` is pinned per grant and reported in authenticated capabilities, completion results, attachment wire and state projections. Task 0 proved R2 enforces the signed base64 `x-amz-checksum-sha256` against actual single-PUT body bytes. Completion records `sha256_verified:true`, `integrity:{algorithm:"sha256",value:<hex>,verified:true}` only after matching metadata/proof checks; pending grants remain unverified. MD5 fallback is parked as historical spike evidence only, with no production profile switch, digest field, client implementation or build task. A failed SHA gate blocks enablement rather than downgrading integrity.

An upload result is `{blob_id,sha256,sha256_verified,integrity,size,retention_class,expires_at}` (`expires_at:null` for `keep`); attachment sends must match the persisted reference fields. Re-upload always makes a new ID and snapshots the current retention class, and old messages stay expired. Reject hash-only R2 requests with authenticated 422 `blob_id_required`; legacy hash-only disk and durable-message requests retain their lookup semantics. Bind new versioned delivery tokens to `(recipient,sha256,blob_id)`; v1 disk tokens never authorize R2.

### 2. Upload grant → immutable PUT → metadata verification → attach

1. `POST /v1/blobs/uploads` with bearer, `Idempotency-Key`, JSON `{size,sha256,media_type}`. Require integer size 1..25 MiB, lowercase 64-hex SHA, valid declared media type ≤128 chars; reject unknown keys. SHA-256 is computed client-side before issuance; reject `content_md5` as an unknown production field. Authenticate/enrollment/scope/rate-limit before R2 calls; accept no URL, key, owner or arbitrary headers.
2. In one SQLite transaction derive uploader, load `snapshot, err := preferences.LoadSnapshot(ctx, tx)` and read `snapshot.Get("blobs.expiry")`, returning `prefs.Effective{Value,Source,Origin,Revision}` plus error, reserve bytes against both the issue day's nonrefundable upload quota and hub storage quota, allocate blob_id/class/key and store the preference snapshot, checksum profile/expected digest/deadlines. Use a transaction-consistent preference read or compare its revision inside the reservation transaction and retry on change. Return 201 `{blob_id,sha256,sha256_verified:false,integrity:{algorithm,value,verified:false},size,retention_class,expires_at,upload:{method:"PUT",url,headers,expires_at},complete_url}`. Pending results never claim verification. Object expiry = grant issue + selected class duration, or null for `keep`; PUT TTL = **5 min** in every class. Preference updates affect new grants only, never an existing object or idempotent replay. Same issuer/idempotency key/body returns the same ID/original deadlines; changed body is 409 `idempotency_conflict`; expired replay never silently issues a fresh grant. Regenerate a retry presign only within the original deadline; never extend it or persist URLs.
3. PUT exact bytes directly to R2 S3, no hub bearer/cookies, redirects disabled. SigV4 scope `<date>/auto/s3/aws4_request`, payload `UNSIGNED-PAYLOAD`. Sign `host`, exact `Content-Length`, `If-None-Match: *`, checksum header, `Content-Type: application/octet-stream`, `Content-Disposition: attachment` and `Cache-Control: private, no-store`. SHA profile uses base64 raw SHA in **signed header** `x-amz-checksum-sha256`; do not hoist it to a query parameter. Sign persisted `x-amz-meta-vecnet-checksum-profile` and `x-amz-meta-vecnet-checksum` as well, for HEAD binding (metadata alone is never proof). Browser supplies Content-Length automatically from a fixed Blob; JS must not set that forbidden header. No chunked/multipart uploads.
4. `POST /v1/blobs/uploads/{blob_id}/complete`, bearer, empty JSON. Only issuer/principal or operator completes, with enabled credential recheck. Hub HEADs **its stored key** without receiving file bytes, checks exact length, signed stored metadata/disposition/cache policy, ETag and any provider checksum. Task 0 establishes the supported checksum evidence: prefer provider-returned SHA checksum; if unavailable, immutable existence plus matching signed checksum metadata is valid only because the spike proved no object can be created through that grant without R2 enforcing that checksum. A missing object is 409 `upload_incomplete`; leave reservation until deadline. Never accept a client PUT receipt, ETag or unsigned metadata as proof. A bucket write by privileged operator credentials is outside the grant threat model; isolate one hub's bucket and protect credentials.
5. CAS pending→complete in SQLite; record checksum profile, provider-verified digest+size, ETag and verification time, move reserved→accepted bytes once. Recheck expiry, issuer eligibility and purge tombstones after HEAD; network is outside transactions. Terminal mismatch rejects/enqueues deletion/charges failed usage. Attach only complete, authorized, unexpired, unpurged IDs in the send transaction. No Worker, verification GET or Fly hashing.

**Quota and replay:** Reserve at issue; do not refund abandoned/failed grants that day. Quota is `reserved + accepted + abandoned + rejected + new size <= daily_limit`; default 500 MiB/day permits twenty full 25 MiB grants including abandoned attempts. Issue day survives midnight/restart; idempotent calls never double-charge. Cap active grants 20/uploader and concurrent completion HEADs 2/hub, with 429 `upload_busy`/Retry-After. Conditional create-only PUT prevents replacement, but a deleted key can be recreated until the presign expires. Keep cleanup jobs through upload deadline+60s and re-delete then; tombstones prevent completion/attachment. These URLs are **as close to one-time upload as possible, not truly single-use**. Presign requests bypass hub rate limiting after issuance, so byte quotas and attempt limits do not bound all R2 replay request charges; monitor provider usage. True consume-once semantics need edge state and are outside the baseline.

### 3. Repeatable authorized get, signed GET, Range and safe rendering

`GET /v1/blobs/{sha256}/download?blob_id=<id>[&t=<token>]` returns `{method:"GET",url,expires_at,object_expires_at,blob_id,sha256,sha256_verified,integrity,size,media_type,retention_class}` and `Cache-Control: no-store`. Accept existing bearer authorization or matching v2 delivery token. Authorize an enabled recipient with current token/history visibility, the authenticated original uploader (including its authorized principal), or the operator; preserve principal and `from_join` checks for recipient/history access. Uploader access to its own completed R2 object is explicit in v4; keep legacy disk/durable authorization unchanged. Check authorization before exposing state, then require complete, unpurged and (`expires_at` is null or `now < expires_at`) before signing. Legacy `GET /v1/blobs/{sha256}?b=<id>&t=...` performs the same checks and returns a 307 to S3, never bytes. Disk/durable paths remain local; grant exchange returns `{local_path}` for them.

**Get whenever needed:** any currently authorized recipient/uploader can call `vecnet_blob_get(sha256,blob_id)`, the HTTP download endpoint above, or `vecnet blob get SHA --blob-id ID --out PATH` at any time while the completed blob is retained and not purged/expired. Each call rechecks current authorization/state and mints a fresh URL with a new capability deadline computed from the current clock; no previous URL or failed download is required. An expired earlier URL never consumes the right to get again. Delivered R2 messages carry the stable reference (`blob_id`, `sha256`, `size`, recorded object `expires_at` and integrity/class fields), **never a URL**: omit signed URLs and legacy tokenized hub `blob_url` decoration for these attachments. Clients construct the authenticated get endpoint from that reference; legacy disk/durable decoration remains compatible. Neither server nor client persists/caches signed URLs for later use; hold them only for the current explicit transfer operation/result. To retrieve later, keep the reference and call get again. Guide/tool text: **“URLs are short-lived; call get again whenever you need the file, as long as it hasn't expired.”**

**Mint limit and metering:** allow **30 URL mints per peer per rolling 60 seconds**, shared across MCP, HTTP/legacy redirects, CLI, web and connector calls, all blobs and all credentials for that identity. Resolve delivery tokens to the recipient peer; principal-only/operator callers use their stable authenticated principal/operator identity with the same limit, never IP/token/blob-specific buckets or a bypass. Apply one concurrency-safe hub-level limiter in `BlobDownload` after authorization/state checks and before provider probes/signing, so adapters cannot double-charge or evade it. The 31st attempt returns HTTP **429 `blob_url_rate_limited`**, `Retry-After` plus `details.retry_after_seconds` until the next slot; MCP returns `isError` with the same code/retry detail and CLI exits nonzero with the machine-readable code. Return **no URL** on rejection. Limit only new capabilities, not transfers using an already-issued URL; it cannot limit direct S3 replays. Emit a sanitized `download_grant_issued` usage event for every successful mint (including every re-mint), uniquely identified per issuance, and `download_grant_rate_limited` for a limiter refusal; include caller/blob ID/status/time, never URLs or invented downloaded bytes. Recheck authorization/expiry/purge before returning a capability after any provider wait. A state change or failed signing emits no successful issuance event.

Issue method-bound S3 SigV4 **GET** for exactly the stored bucket/key on `https://<account>.r2.cloudflarestorage.com`, with `X-Amz-Expires = floor(min(600s, object_expires_at-now))` for expiring classes; for `keep`, use **600 s (10 min)** and return `object_expires_at:null`. Decline if <1 second remains for expiring objects. `off` disables object time expiry only; it never creates permanent download capabilities. Ten minutes accommodates host scheduling and up to 25 MiB transfers; never issue beyond the logical object deadline. Each later get starts a fresh capability window within the same immutable object deadline, subject to current authorization and the mint limit. PUT TTL remains **5 min**: v4 changes download scheduling, with no reason to extend upload replay exposure. Sign exact response override parameters only where confirmed by Task 0/provider acceptance; baseline relies on immutable stored octet-stream/disposition/cache metadata. HEAD, PUT and DELETE require separate signatures; no arbitrary method/path/endpoint or client-selected response headers. Validate Range behavior (206/416, full/open/suffix, reject unsupported multi-range at the client), size bounds and Range CORS against S3. Clients do not treat partial ranges as full digest verification.

All clients use credential-free direct transport, fixed allowed endpoint from authenticated capabilities, no redirects, bounded streaming and no arbitrary `origin_url` fetch. Web fetches into a Blob then a download action with a sanitized local name; never inline SVG/HTML or untrusted images. R2 stores `application/octet-stream`, `Content-Disposition: attachment`, `Cache-Control: private, no-store`; original media type and filename are display metadata only, not trusted sniff results. Strip controls/bidi/path separators/CRLF, limit filename to 255 code points, use `textContent` for durable text. Verify actual final S3 response headers in acceptance.

**Baseline security limitation:** S3 cannot be assumed to support custom `X-Content-Type-Options`, CSP or Referrer-Policy response overrides. A hub redirect cannot add these to the final S3 response. We accept attachment-only stored metadata, client-controlled safe saving and no inline rendering in the no-Worker baseline; do not falsely promise those extra headers.

Already-issued S3 GETs are replayable until their **≤600 s (10 min)** deadline after recipient disable/token revocation. Purge deletes the object and prevents future grants, but is not instant individual-URL revocation. Every re-mint checks current eligibility; disabled/revoked callers cannot extend access by getting again. Treat expiration as a request-start boundary (include provider behavior in Task 0 acceptance); bytes already downloaded or a transfer begun before expiry cannot be clawed back. Hub logical expiry blocks new grants/references exactly at each recorded expiring-class deadline; `keep` remains eligible while retained and not purged, including its pre-first-attach window. Expiring-object URLs are bounded by the recorded deadline; keep URLs still expire within 600s. Buckets have no public r2.dev or public custom-domain access. True single-use GETs need an edge component with atomic used-token state; such work is outside this plan.

### Security: ephemeral URLs in MCP model context

Max explicitly chooses URL-bearing MCP tool results. Treat each URL as a bearer capability: a model, transcript, MCP host telemetry or someone reading a retained tool result can replay/leak it within TTL. Assume the intended hosts can HTTP-transfer files and the upload/download domains are allowed; return URLs only on explicit authenticated blob transfer tool calls, never unsolicited inbox/history/resources/events or stored Message fields. Scope to one key, one method, exact upload length/checksum/conditional headers and the minimum practical TTL; issue neither bucket credentials nor list/delete capabilities. MCP hosts make requests themselves and omit hub auth/cookies. Do not offer a tool that fetches an arbitrary model-supplied URL through Fly.

Set `Cache-Control: no-store` on hub/MCP HTTP responses, mark URL fields sensitive in schemas/descriptions, redact all URL queries/signatures/credentials from server logs, traces, exceptions and audit details; usage records contain IDs/status/bytes only. Operator/host guidance disables tool-result/request-URL logging or redacts these fields where supported, and never pastes live URLs into tickets/chat. This cannot guarantee external transcript deletion: short TTL and narrow scope bound exposure. URLs must exist in the deliberate tool result; do not apply generic token-stripping there, while continuing to strip delivery tokens and URLs from every other MCP representation. No tool result claims either upload or download is truly single-use.

### 4. Expiry, metadata, durable text and avatars

Consume the prefs Task 1 registry definition of `blobs.expiry`, default `1d` (24 h); this plan supplies its backend capability/consumer adapter. Use this deliberately finite set; arbitrary durations are rejected so every expiring class has an operator-installed lifecycle rule:

| Preference value | Recorded class | Logical deadline from grant issue | Key suffix under `attachments/v1/` | Lifecycle `Expiration.Days` |
|---|---|---|---|---|
| `1h` | `1h` | +1 h | `exp/1h/<hub_namespace>/<blob_id>` | 1 |
| `6h` | `6h` | +6 h | `exp/6h/<hub_namespace>/<blob_id>` | 1 |
| `12h` | `12h` | +12 h | `exp/12h/<hub_namespace>/<blob_id>` | 1 |
| `1d` (default) | `1d` | +24 h | `exp/1d/<hub_namespace>/<blob_id>` | 1 |
| `7d` | `7d` | +7 d | `exp/7d/<hub_namespace>/<blob_id>` | 7 |
| `30d` | `30d` | +30 d | `exp/30d/<hub_namespace>/<blob_id>` | 30 |
| `off` | `keep` | none (`expires_at:null`) | `keep/<hub_namespace>/<blob_id>` | **none** |

The selected value, source and preference revision are snapshotted at grant issuance. Object keys, recorded class and deadline never change afterwards: switching `1d`→`off` does not rescue old expiring objects, and switching `off`→`1d` leaves existing referenced `keep` objects retained. Idempotent grant replays use their original snapshot. Pins do not extend expiring deadlines. For `keep`, retain while any retained message reference exists, until explicit purge or last-reference GC. A completed keep upload must gain its first reference within 24 h of completion; otherwise mark it abandoned and enqueue deletion. Pending grants expire after five minutes even with `off`; failed/abandoned grants are cleaned up. Attach and GC use a transaction/CAS so GC cannot delete a newly referenced object; once cleanup is scheduled, late attach fails.

A 30-second ticker marks expiring objects expired at their recorded deadline and enqueues deletion with bounded retry/backoff. It skips time expiry for `keep`, but still handles purge, failed grants and reference GC. GET signing and reads check the clock without waiting for the ticker. Preserve the default multipart-abort-only rule, which cannot expire completed keep objects. Do not use HTTP `Expires` as deletion.
