# R2 Blobs with Direct Transfers and Configurable Retention Implementation Plan

> **For agentic workers:** Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement task by task. Follow the house task/review gates in `docs/plans/2026-11-05-hub-notices.md`. Steps use checkbox (`- [ ]`) syntax. A `---` ends every task. This document is a plan; its creation does not authorize deployment or resource creation.

**Goal:** Fly-hosted hubs authorize private, signed transfers for new R2 attachments whose file bytes never traverse Fly, with retention set through the web UI using shared typed hub preference `blobs.expiry` (default 24 h; supported classes 1 h..30 d or `off`). Local hubs retain their disk backend; existing hosted disk files remain grandfathered.

**Architecture:** Keep authorization, reservations, object state and message references in SQLite. The free-tier baseline has **no Worker**: clients and HTTP-capable MCP hosts PUT/GET directly on the private R2 S3 endpoint using stdlib SigV4 presigns. Sign exact Content-Length and a provider-enforced checksum; prefer SHA-256 only after the first real-bucket spike passes, otherwise use signed Content-MD5 with verified MD5+size identity and explicitly unverified client-declared SHA-256 metadata. R2 keys use grant IDs, with no cross-uploader dedupe. Retention-class prefixes isolate expiring objects from `keep/` objects; a finite hub storage quota bounds all outstanding grants and retained bytes. Custom-domain downloads and their Worker task are explicitly dropped; clients can whitelist the private S3 endpoint. Persistent message text and avatars remain database content, outside attachment expiry; existing Fly disk files are grandfathered without migration.

**Tech Stack:** Existing Go toolchain, `CGO_ENABLED=0`, Go stdlib `crypto/hmac`, `crypto/sha256`, `crypto/md5` (transfer checksum only), `encoding/xml`, `net/http`; vanilla browser modules; Node connector code. No AWS SDK or new Go module. No Worker or Worker tooling is planned.

## Current behavior and implications

- `internal/blob/store.go` streams to disk, hashes, dedupes globally, charges 25 MiB/file and 500 MiB/uploader/UTC day defaults, and records all uploaders. Its GC removes only **unreferenced** bytes; pins override TTL. Neither that TTL nor the seven-day HMAC read-token lifetime implements this requirement.
- `internal/httpapi/blobs.go` currently receives PUT bodies and serves seekable GETs with Range, `nosniff` and CSP sandbox. `internal/hub/blobs.go` authorizes a recipient token (including an enabled-peer check), operator, or history-visible thread participant. `checkAttachments` in `internal/hub/spill.go` prevents hash guessing from granting attachment access.
- `spill.go` stores full long text as a blob uploaded by `hub`, then emits a preview and `message.md`. `internal/hub/sources.go:IngestSource` also stores source raw JSON as an attachment. Both need an explicit durable message-data path before R2 is enabled.
- Contrary to the assignment's premise about avatars, `internal/hub/avatar.go` already normalizes images and stores PNG bytes in `avatars.png` in SQLite (migration `0016_peer_avatars.sql`). Preserve that behavior; do not migrate avatars to expiring storage.
- CLI `app.upload` in `internal/cli/commands.go`, `internal/opclient.Client.Upload/Blob` (also used by the TUI), web `api.js`, and connector `HubApi.putBlob/fetchBlob` are separate transfer entry points. There is currently no top-level `vecnet blob get` command; add it rather than referring users to a nonexistent command.
- MCP currently accepts 160 KiB decoded PUTs and returns 128 KiB base64 GET pages, deliberately stripping delivery read tokens. Maintaining those byte paths for remote attachments would violate the Fly constraint even at their present small caps.

## Decisions and wire contracts

### 1. Isolated objects, checksums and attachment identity

Add optional `blob_id` to the attachment schema and require it for new R2 uploads. IDs are server-generated `blo_` plus a 26-character Crockford base32 encoding of 128 cryptographically random bits (first character 0–7). Use a random-ID mint rather than timestamp ULIDs. IDs confer no authority. Each grant allocates one key `attachments/v1/<hub_namespace>/exp/<class>/<blob_id>` or `attachments/v1/<hub_namespace>/keep/<blob_id>` for `off`; the namespace is random and persisted in SQLite. Keys contain no filenames, uploader IDs or client paths. **The key is the grant ID, never a content hash**, in both checksum profiles. No cross-uploader or cross-generation dedupe: independent grant-time retention and small files make dedupe savings minor, while isolation avoids existence leaks and retention coupling. Disk dedupe remains unchanged.

Checksum profile is pinned per grant and reported in authenticated capabilities, completion results, attachment wire and state projections:

- `sha256`: selected only if Task 0 proves R2 enforces the signed base64 `x-amz-checksum-sha256` against actual single-PUT body bytes. The wire `sha256` is verified by R2's enforced checksum and hub metadata checks; record `sha256_verified:true`, `integrity:{algorithm:"sha256",value:<hex>,verified:true}`.
- `md5`: selected if that SHA test fails but signed Content-MD5 succeeds. **Choose verified MD5+size as the hub identity**, scoped to blob_id; retain the attachment's existing `sha256` field solely as client-declared compatibility metadata, with explicit `sha256_verified:false` and `integrity:{algorithm:"md5",value:<base64>,verified:true}`. This keeps existing routes and old consumers working without advertising collision-resistant content addressing. New clients must display/consume the trust flag; hub ownership/visibility/attach/purge lookups use blob_id, never the unverified SHA as proof or a dedupe key. A claimed SHA tombstone can conservatively reject the claim, but cannot prove a fallback upload's content; document that limitation of hash-level purge. MD5+size detects transfer corruption, not malicious MD5 collisions.

An upload result is `{blob_id,sha256,sha256_verified,integrity,size,retention_class,expires_at}` (`expires_at:null` for `keep`); attachment sends must match the persisted reference fields. Re-upload always makes a new ID and snapshots the current retention class, and old messages stay expired. Reject hash-only R2 requests with authenticated 422 `blob_id_required`; legacy hash-only disk and durable-message requests retain their lookup semantics. Bind new versioned delivery tokens to `(recipient,sha256,blob_id)`; v1 disk tokens never authorize R2. The SHA route segment in fallback mode is a compatibility label, not authorization or a verified identity.

### 2. Upload grant → immutable PUT → metadata verification → attach

1. `POST /v1/blobs/uploads` with bearer, `Idempotency-Key`, JSON `{size,sha256,content_md5,media_type}`. Require integer size 1..25 MiB, lowercase 64-hex SHA, canonical 16-byte base64 MD5, valid declared media type ≤128 chars; reject unknown keys. Both digests are computed client-side before issuance so the same request works with either pinned profile. Authenticate/enrollment/scope/rate-limit before R2 calls; accept no URL, key, owner or arbitrary headers.
2. In one SQLite transaction derive uploader, read `prefs.Get(ctx, "blobs.expiry")` with value/source/revision, reserve bytes against both the issue day's nonrefundable upload quota and hub storage quota, allocate blob_id/class/key and store the preference snapshot, checksum profile/expected digest/deadlines. Use a transaction-consistent preference read or compare its revision inside the reservation transaction and retry on change. Return 201 `{blob_id,sha256,sha256_verified:false,integrity:{algorithm,value,verified:false},size,retention_class,expires_at,upload:{method:"PUT",url,headers,expires_at},complete_url}`. Pending results never claim verification. Object expiry = grant issue + selected class duration, or null for `keep`; PUT TTL = **5 min** in every class. Preference updates affect new grants only, never an existing object or idempotent replay. Same issuer/idempotency key/body returns the same ID/original deadlines; changed body is 409 `idempotency_conflict`; expired replay never silently issues a fresh grant. Regenerate a retry presign only within the original deadline; never extend it or persist URLs.
3. PUT exact bytes directly to R2 S3, no hub bearer/cookies, redirects disabled. SigV4 scope `<date>/auto/s3/aws4_request`, payload `UNSIGNED-PAYLOAD`. Sign `host`, exact `Content-Length`, `If-None-Match: *`, checksum header, `Content-Type: application/octet-stream`, `Content-Disposition: attachment` and `Cache-Control: private, no-store`. SHA profile uses base64 raw SHA in **signed header** `x-amz-checksum-sha256`; do not hoist it to a query parameter. MD5 profile uses base64 raw MD5 in signed `Content-MD5`. Sign persisted `x-amz-meta-vecnet-checksum-profile` and `x-amz-meta-vecnet-checksum` as well, for HEAD binding (metadata alone is never proof). Browser supplies Content-Length automatically from a fixed Blob; JS must not set that forbidden header. No chunked/multipart uploads.
4. `POST /v1/blobs/uploads/{blob_id}/complete`, bearer, empty JSON. Only issuer/principal or operator completes, with enabled credential recheck. Hub HEADs **its stored key** without receiving file bytes, checks exact length, signed stored metadata/disposition/cache policy, ETag and any provider checksum. Task 0 establishes the supported checksum evidence: prefer provider-returned SHA checksum; if unavailable, immutable existence plus matching signed checksum metadata is valid only because the spike proved no object can be created through that grant without R2 enforcing that checksum. MD5 profile must check the real-bucket-proven single-PUT MD5/ETag and size. A missing object is 409 `upload_incomplete`; leave reservation until deadline. Never accept a client PUT receipt, ETag or unsigned metadata as proof. A bucket write by privileged operator credentials is outside the grant threat model; isolate one hub's bucket and protect credentials.
5. CAS pending→complete in SQLite; record checksum profile, provider-verified digest+size, ETag and verification time, move reserved→accepted bytes once. For MD5 record `sha256_verified:false` permanently; no claimed SHA content addressing. Recheck expiry, issuer eligibility and purge tombstones after HEAD; network is outside transactions. Terminal mismatch rejects/enqueues deletion/charges failed usage. Attach only complete, authorized, unexpired, unpurged IDs in the send transaction. No Worker, verification GET or Fly hashing.

**Quota and replay:** Reserve at issue; do not refund abandoned/failed grants that day. Quota is `reserved + accepted + abandoned + rejected + new size <= daily_limit`; default 500 MiB/day permits twenty full 25 MiB grants including abandoned attempts. Issue day survives midnight/restart; idempotent calls never double-charge. Cap active grants 20/uploader and concurrent completion HEADs 2/hub, with 429 `upload_busy`/Retry-After. Conditional create-only PUT prevents replacement, but a deleted key can be recreated until the presign expires. Keep cleanup jobs through upload deadline+60s and re-delete then; tombstones prevent completion/attachment. These URLs are **as close to one-time upload as possible, not truly single-use**. Presign requests bypass hub rate limiting after issuance, so byte quotas and attempt limits do not bound all R2 replay request charges; monitor provider usage. True consume-once semantics need edge state and are outside the baseline.

### 3. Authorized signed GET, Range and safe rendering

`GET /v1/blobs/{sha256}/download?blob_id=<id>[&t=<token>]` returns `{method:"GET",url,expires_at,object_expires_at,blob_id,sha256,sha256_verified,integrity,size,media_type,retention_class}` and `Cache-Control: no-store`. Accept existing bearer authorization or matching v2 delivery token; check enabled recipient, principal/history visibility, complete state, purge and (`expires_at` is null or `now < expires_at`) before signing. Upload ownership alone does not grant read permission. Legacy `GET /v1/blobs/{sha256}?b=<id>&t=...` performs the same checks and returns a 307 to S3, never bytes. Disk/durable paths remain local; grant exchange returns `{local_path}` for them.

Issue method-bound S3 SigV4 **GET** for exactly the stored bucket/key on `https://<account>.r2.cloudflarestorage.com`, with `X-Amz-Expires = floor(min(120s, object_expires_at-now))` for expiring classes; for `keep`, use 120s and return `object_expires_at:null`. Decline if <1 second remains for expiring objects. `off` disables object time expiry only; it never creates permanent download capabilities. **Two minutes is the shortest practical default** for host scheduling and up to 25 MiB transfers; never issue beyond the logical object deadline, and reacquire once if an unused URL expires. Sign exact response override parameters only where confirmed by Task 0/provider acceptance; baseline relies on immutable stored octet-stream/disposition/cache metadata. HEAD, PUT and DELETE require separate signatures; no arbitrary method/path/endpoint or client-selected response headers. Validate Range behavior (206/416, full/open/suffix, reject unsupported multi-range at the client), size bounds and Range CORS against S3. Clients do not treat partial ranges as full digest verification.

All clients use credential-free direct transport, fixed allowed endpoint from authenticated capabilities, no redirects, bounded streaming and no arbitrary `origin_url` fetch. Web fetches into a Blob then a download action with a sanitized local name; never inline SVG/HTML or untrusted images. R2 stores `application/octet-stream`, `Content-Disposition: attachment`, `Cache-Control: private, no-store`; original media type and filename are display metadata only, not trusted sniff results. Strip controls/bidi/path separators/CRLF, limit filename to 255 code points, use `textContent` for durable text. Verify actual final S3 response headers in acceptance.

**Baseline security limitation:** S3 cannot be assumed to support custom `X-Content-Type-Options`, CSP or Referrer-Policy response overrides. A hub redirect cannot add these to the final S3 response. We accept attachment-only stored metadata, client-controlled safe saving and no inline rendering in the no-Worker baseline; do not falsely promise those extra headers.

Already-issued S3 GETs are replayable until their ≤120s deadline after recipient disable/token revocation. Purge deletes the object and prevents future grants, but is not instant individual-URL revocation. Treat expiration as a request-start boundary (include provider behavior in Task 0 acceptance); bytes already downloaded or a transfer begun before expiry cannot be clawed back. Hub logical expiry blocks new grants/references exactly at each recorded expiring-class deadline; `keep` remains eligible while referenced and not purged. Expiring-object URLs are bounded by the recorded deadline; keep URLs still expire within 120s. Buckets have no public r2.dev or public custom-domain access. True single-use GETs need an edge component with atomic used-token state; such work is outside this plan.

### Security: ephemeral URLs in MCP model context

Max explicitly chooses URL-bearing MCP tool results. Treat each URL as a bearer capability: a model, transcript, MCP host telemetry or someone reading a retained tool result can replay/leak it within TTL. Assume the intended hosts can HTTP-transfer files and the upload/download domains are allowed; return URLs only on explicit authenticated blob transfer tool calls, never unsolicited inbox/history/resources/events or stored Message fields. Scope to one key, one method, exact upload length/checksum/conditional headers and the minimum practical TTL; issue neither bucket credentials nor list/delete capabilities. MCP hosts make requests themselves and omit hub auth/cookies. Do not offer a tool that fetches an arbitrary model-supplied URL through Fly.

Set `Cache-Control: no-store` on hub/MCP HTTP responses, mark URL fields sensitive in schemas/descriptions, redact all URL queries/signatures/credentials from server logs, traces, exceptions and audit details; usage records contain IDs/status/bytes only. Operator/host guidance disables tool-result/request-URL logging or redacts these fields where supported, and never pastes live URLs into tickets/chat. This cannot guarantee external transcript deletion: short TTL and narrow scope bound exposure. URLs must exist in the deliberate tool result; do not apply generic token-stripping there, while continuing to strip delivery tokens and URLs from every other MCP representation. No tool result claims either upload or download is truly single-use.

### 4. Expiry, metadata, durable text and avatars

Register `blobs.expiry` in the shared typed hub-preferences registry, default `1d` (24 h). Use this deliberately finite set; arbitrary durations are rejected so every expiring class has an operator-installed lifecycle rule:

| Preference value | Recorded class | Logical deadline from grant issue | Key suffix under `attachments/v1/<hub_namespace>/` | Lifecycle `Expiration.Days` |
|---|---|---|---|---|
| `1h` | `1h` | +1 h | `exp/1h/<blob_id>` | 1 |
| `6h` | `6h` | +6 h | `exp/6h/<blob_id>` | 1 |
| `12h` | `12h` | +12 h | `exp/12h/<blob_id>` | 1 |
| `1d` (default) | `1d` | +24 h | `exp/1d/<blob_id>` | 1 |
| `7d` | `7d` | +7 d | `exp/7d/<blob_id>` | 7 |
| `30d` | `30d` | +30 d | `exp/30d/<blob_id>` | 30 |
| `off` | `keep` | none (`expires_at:null`) | `keep/<blob_id>` | **none** |

The selected value, source and preference revision are snapshotted at grant issuance. Object keys, recorded class and deadline never change afterwards: switching `1d`→`off` does not rescue old expiring objects, and switching `off`→`1d` leaves existing referenced `keep` objects retained. Idempotent grant replays use their original snapshot. Pins do not extend expiring deadlines. For `keep`, retain while any retained message reference exists, until explicit purge or last-reference GC. A completed keep upload must gain its first reference within 24 h of completion; otherwise mark it abandoned and enqueue deletion. Pending grants expire after five minutes even with `off`; failed/abandoned grants are cleaned up. Attach and GC use a transaction/CAS so GC cannot delete a newly referenced object; once cleanup is scheduled, late attach fails.

A 30-second ticker marks expiring objects expired at their recorded deadline and enqueues deletion with bounded retry/backoff. It skips time expiry for `keep`, but still handles purge, failed grants and reference GC. GET signing and reads check the clock without waiting for the ticker. Lifecycle rules match **only** the six explicit expiring prefixes in the table; no all-prefix or parent `attachments/v1/` rule is safe. Day-granularity lifecycle supplies eventual disaster cleanup, not the exact application deadline; subday classes rely on hub deletion for prompt cleanup. `keep` has no provider disaster expiry, so backups, quota and restart-safe reference GC matter. Do not use HTTP `Expires` as deletion. UI says **“Attachment expired (<recorded duration> retention)”**, including “Attachment expired (24-hour retention)” for the default, or **“Kept while referenced”** for `keep`; never promise exact physical deletion.

**Shared preference interface (consumed, not a second store):** `git show plan-prefs:docs/plans/2026-11-05-hub-preferences.md` found no document in this planning pass. Before implementation, read that branch's then-current plan and reconcile this contract. Consume `prefs.Get(ctx, "blobs.expiry") -> {value,source,revision}` (source identifies default or persisted override), typed registry validation/defaults, revisioned change notifications (`prefs.Subscribe(ctx, "blobs.expiry")`), and the shared operator mutation/audit path. Notifications refresh capabilities/settings immediately; missed events trigger re-read on reconnect and every grant uses an authoritative revision. Persist no duplicate blob-specific preference table or independent settings endpoint. Preference read failures fail new grants closed; absence of an override uses the registered default. Notifications/capabilities must not import SQLite into CLI wire/client packages.

Only authenticated hub operators can update this hub-wide preference through the shared web settings UI/API. Ordinary peers see recorded per-object retention, not a write control. Show current value/source and explain **“Applies to new uploads only”** with existing class counts/bytes. On a hosted hub, selecting `off` requires a separate explicit operator confirmation acknowledging ongoing storage cost, retained used/limit bytes, and lack of automatic disaster expiry; enforce this on the server-side shared mutation path too (including non-UI callers), with stale-revision rejection and an audit entry recording actor, old/new value/source/revision and confirmation, never URLs/secrets. No localStorage-only setting or unchecked alternate writer. Reverting to a duration needs no cost confirmation and does not delete existing kept files. Missing finite storage quota blocks enabling `off`; lowering a limit below current usage stops new grants and displays over-limit state without deleting referenced data.

**Retained storage bound:** a separate hub-wide `--r2-storage-quota-bytes` / `VECNET_R2_STORAGE_QUOTA_BYTES` is a finite positive integer (default **5 GiB**); zero/unlimited is invalid for R2. Apply it to **all classes** so a preference change cannot evade it. In the same reservation transaction as the daily quota, require `storage_reserved_bytes + retained_bytes + new_size <= storage_limit_bytes`; reject with authorized 429 `blob_storage_quota_exceeded`, no PUT capability. Include used/limit only for operator callers; peers receive the code without hub-wide aggregates. Reserved bytes cover every still-usable grant; completion moves them to retained bytes once. Abandoned/rejected/purged/expired objects continue to consume their reserved/retained charge until deletion or absence is confirmed **after upload_deadline+60s**, preventing a live presign recreation from reclaiming capacity early. Retry/restart reconciliation never double-counts or releases uncertain objects. Provider deletion lag/outages therefore stop new grants safely. The UI shows retained, reserved, total used and limit bytes, updates after transitions/reconnect, and links to purge/reference cleanup; operator-only aggregates avoid leaking others' usage. This bounds hub-authorized storage, not operator out-of-band writes or all billable replay requests; retain provider monitoring and account-wide allowance checks.
