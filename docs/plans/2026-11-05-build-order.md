## Parallel worktrees and merge ownership

No pair of whole plans is safe for unrestricted concurrent edits. Parallel work is safe only when workers receive disjoint file scopes; shared-file integration is serialized and rebased onto the preceding merge.

| Parallel work that can avoid file conflicts | Required ownership split |
|---|---|
| DB hydration vs R2 signer/wire vs prefs registry preparation | DB owns new `internal/eventpayload/**`; R2 owns new `internal/blob/r2sign*`, `r2meta*`, `r2store*`, `internal/blobwire/**`; prefs owns new `internal/prefs/**`. Existing envelope schemas, store tests, migrations and hub wiring are excluded from these parallel slices and assigned to integration commits. |
| Prefs CLI/TUI vs prefs web after HTTP | CLI worker owns prefs command files and `internal/{cli,opclient,tui}/**`; web owns `internal/ui/static/{settings*,appearance*}`, UI tests and `scripts/ui/prefs.mjs`. Serialize any shared opapi DTO edits; R2/admin client changes wait for these commits. |
| R2 transfers vs Settings rendering | R2 worker owns `internal/blob/{transfers*,durable*,usage*}` and attachment components only; prefs owns Settings draft/model/views. `api.js`, hub wiring and quota/confirmation UI adapters integrate serially after these slices; never implement two Settings stores. |
| Admin contract preparation vs consumer implementation | Admin worker owns new `docs/admin-operations.json`, new `internal/adminops/**` descriptors and new conformance scripts. Existing hub/auth/HTTP/MCP/CLI/UI wiring, envelope types and shared docs are excluded until rebased integration. |

Likely conflict files: `internal/hub/{hub.go,tickers.go,send.go,history.go,spill.go,provision.go}`, `cmd/vecnet-hub/{main.go,main_test.go}`, `internal/store/{store.go,store_test.go,migrations/*}`, `internal/events/{store.go,worker.go}`, `internal/httpapi/{admin.go,middleware.go,events.go}`, `internal/opapi/types.go`, `internal/envelope/{types.go,schema.json}`, `docs/protocol/envelope.schema.json`, `internal/{cli,opclient}/` dispatch/client files, `internal/mcpserver/{server.go,tools.go,resources.go,events.go}` (discover actual registration files), `internal/ui/static/{api.js,app.js,index.html,settings.js,settings-model.js}`, `internal/tui/` API/navigation, screenshot README/index, `docs/{PROTOCOL,OPERATOR,DEPLOY}.md`, `CHANGELOG.md` and `justfile`. Default integration order for these touch points is prefs core → DB → R2 → prefs clients/Settings → admin → TUI forms; each plan's internal task ordering still applies. Documentation sections and schemas get one integrator, not simultaneous whole-file rewrites.
