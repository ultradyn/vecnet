# vecnet Launcher (P1, P2) and Principal Peer Provisioning Implementation Plan

> **For agentic workers:** executed by `docs/plans/vecnet-core-build.workflow.mjs` with `docs/plans/launcher.workflow-args.json` (written by the coordinator from this plan). Each task runs in its own worktree from the dependency map and sees only its own section plus the Global Constraints. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Any enrolled agent can start a coding-agent session on a host by sending a `launch` job to that host's launcher peer, then talk to the session in the job thread, answer its questions, and approve its permission prompts. P1 runs the `t3` backend on xsm; P2 adds `paseo` on xsm, `t3` on the build boxes, and the two-timer idle model. Alongside it, issue 28 lets a principal create, disable and re-enable its own peers within operator-set limits.

**Architecture:**
- **Hub (Go).** The `launcher` peer kind with a 15-minute presence TTL; a 7-day cap on a sender-chosen `expires_at`; issue 28 in full (`POST /v1/peers`, `PATCH /v1/peers/{id}`, principal limits and default scopes, `created_by` in the directory); a kind colour and a principals card in the operator UI; PROTOCOL §18 and the §13.8 launcher checklist. Nothing else in the hub changes: jobs, threads and approvals already carry the launcher's wire.
- **Shared hub client (TypeScript).** `connectors/hub-client/` holds the wire types, SSE parser, resumable stream and HTTP client. Its interfaces are exactly the openclaw plan's Tasks 1–4 (`docs/plans/2026-11-01-openclaw-plugin.md`), which has not been built yet, so openclaw imports this package instead of writing its own (design D7, §1.2).
- **Launcher daemon (TypeScript on Node, zero runtime dependencies).** One per host, a pull client with a peer credential. Inbound flow: SSE event → ingress row in a `node:sqlite` ledger → cursor saved and acked → dispatcher → per-session lane → backend plugin. Outbound sends go through a ledger outbox with deterministic idempotency keys, so a crash never loses or doubles a post. Backends are plugins behind the design's `Backend` / `SessionHandle` contract; `t3` and `paseo` drive the bridges' existing CLIs, unmodified.

**Tech Stack:** Go 1.26 (`CGO_ENABLED=0`), SQLite migrations, vanilla ES modules in `internal/ui/static/`, Bubble Tea v2. TypeScript run directly by Node's built-in type stripping (Node ≥ 22.18; xsm has 22.23.3, x-tuf 22.22.1, x-tall 24.22.1, x-p35 24.22.0), `node:test`, `node:sqlite`, `fetch`. Dev-only dependencies, exact versions, nothing at runtime: `typescript@7.0.2` (type-check only, the version pag-chat already uses on xsm) and `@types/node` (latest 22.x, for `node:sqlite` and `node:test` types). pnpm 10 installs them.

**Spec:** `docs/design/2026-11-03-launcher.md` (cited as [D]; decisions §10 D1–D9, §10.1 A1–A8, §10.2 D10–D13). `.scratch/vecnet/issues/28-principal-peer-provisioning.md` (frozen with pag-chat, revised 2026-11-03: active-peer cap, `--creates-per-hour`). `.scratch/vecnet/issues/26-agent-sources.md`. PROTOCOL §2, §5.6, §6, §8, §9, §12, §13.1, §16. Bridges read for this plan, never modified: `~/src/t3-bridge` (`README.md`, `src/cli/commands/*.mjs`, `src/t3/launch.mjs`, `docs-mcp-tools.json`) and `~/src/paseo-bridge` (`README.md`, `paseo_bridge/cli.py`).

**Starts from:** `master` after the reactions build merges. Reactions takes migration `0012` and PROTOCOL §17 and creates `CHANGELOG.md`; this plan takes `0013` and §18 and appends to that changelog. Master today ends at `0011_inbox_indexes.sql`, and no other open branch adds a migration.

## Global Constraints

### Hub (Tasks 1–5)
- Builds and tests: `build2 go test -p 2 …`, `build2 node --test --test-concurrency=2 …`, `CGO_ENABLED=0 build2 go build -p 2 -o bin/ ./cmd/...`.
- `internal/envelope/schema.json` does not change, and neither do the demo seed (`internal/opseed`) nor any golden file not named in a task. Tests create launcher and principal-created peers at run time.
- Error codes are those of PROTOCOL §15 plus the three issue 28 codes: 403 `kind_not_allowed`, 429 `peer_cap_reached` (`details {limit, active, disabled}`), 429 `peer_create_rate_limited` (`details.retry_after_seconds`, plus `Retry-After` from the existing `writeError`).
- **Issue 28 wire shapes are frozen with pag-chat.** Do not rename a field:
  - `POST /v1/peers {kind, name, idempotency_key}` with a principal credential → `201 {"peer": {"peer_id", "kind", "name", "created_by", "disabled": false}, "idempotency_key"}`. A replay of the same key within 24 h with the same body returns the original response with 200; a different body is 409 `idempotency_conflict` with `details.idempotency_key`.
  - `PATCH /v1/peers/{id} {disabled: true|false}` → `200 {"peer": {…same object, current disabled…}}`. Only for peers the caller created **and** still owns (`created_by` = caller and `prn_id` = caller); any other id is 404 `not_found`.
  - `GET /v1/peers` entries carry `created_by` (a `prn_` id) on principal-created peers; the key is absent on operator-enrolled peers.
- A test marked **(guard)** passes before its task's change and must keep passing; every other listed test fails first.

### Daemon (Tasks 6–18)
- **Location:** `connectors/hub-client/` (shared) and `connectors/launcher/`. Neither imports the other's `node_modules`; `hub-client` has no `package.json` dependencies at all.
- **TypeScript runs as written.** Erasable syntax only (no `enum`, `namespace`, parameter properties or `import =`); relative imports end in `.ts`; type-only imports use `import type`. `tsconfig.json`: `strict`, `module`/`moduleResolution: "nodenext"`, `target: "es2023"`, `noEmit`, `allowImportingTsExtensions`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `types: ["node"]`, `include` covering both packages' `src`, `test` and `testing`.
- **Commands:** every build or test goes through a `just ln-*` recipe (Task 6), which runs `build2` with at most 2 workers. Never run `node --test`, `tsc` or `pnpm install` bare. Each worktree runs `just ln-setup` once.
- **No runtime dependencies.** `dependencies` stays empty in both `package.json` files; `test/boundary.test.ts` (Task 6) enforces it.
- **Plugins** (`src/backends/**`) import only `../../backend.ts`, their own files and `node:*`. They never see the hub client, the credential, the hub URL or a raw Delivery (enforced by the boundary test).
- **Authorisation** is keyed only on the authenticated `sender`, plus the hub-set `created_by` from the directory for principal policy keys. Never on names, content, `capabilities` or self-reported tags (PROTOCOL §14.1).
- **Secrets and bodies** never reach logs, thrown messages, job output or presence. The credential is read from a 0600 file; a looser mode refuses to start. Every agent environment passes through `scrubEnv` (Task 8).
- **Clock:** every timer goes through the `Clock` port (`hub-client/src/ports.ts`); tests use `fakeClock()`.
- **Ids and keys.** Ids are opaque and copied from the hub. Idempotency keys are pre-assigned per purpose so tasks cannot collide (all match `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`):

| Prefix | Purpose | Owner |
|---|---|---|
| `vl.js.<job_id>.<seq>` | `job_status` | Task 9 |
| `vl.tr.<job_id>.<turn_hash>` | turn-result reply (`turn_hash` = first 24 hex of sha256(turn_id)) | Task 11 |
| `vl.nt.<job_id>.<purpose>.<n>` | launcher notes in a job thread | Tasks 11, 12, 17 |
| `vl.ar.<approval_id>` | `approval_request` | Task 12 |
| `vl.ac.<approval_id>` | `launch.approval_closed` notice | Task 12 |
| `vl.q.<job_id>.<question_hash>` | `launch.question` message | Task 12 |
| `vl.es.<job_id>.<n>` | first message of a job's operator-escalation thread | Task 12 |

- **Wire conventions** ([D] §3; normative in PROTOCOL §13.8, Task 5):
  - Turn replies: `in_reply_to` = last consumed message; recipients = the thread default; priority = `input.reply_priority` (default `wake_idle`); `metadata` = `{"launch.turn", "launch.turn_id", "launch.job_id", "launch.consumed"}`.
  - `job_status` priority: `hold` for `accepted` and `running`, `wake_idle` for `succeeded`, `failed` and `cancelled`.
  - Permission prompts: `approval_request` to the requester with `metadata["launch.permission"]` v1 ([D] §3.5, closed schema), options = the backend's labels plus `escalate` when the route allows it, `escalate_to_operator: true` unless the route says otherwise, priority `wake`.
  - Escalations and direct-to-operator prompts go into a **per-job escalation thread** the launcher opens to the operator (`thread_title: "vl escalation: <job title>"`, `metadata["launch.job_id"]`), because a requester-locked job thread refuses a new participant (§16.3 `participants_locked`).
  - Questions: `kind: message` to the requester, priority `wake`, `metadata["launch.question"]` v1.
- **Text limits:** relayed input per backend send ≤ 96 KiB (`MAX_TURN_INPUT_BYTES`); the rest queues as the next input. Replies over 4 KiB are spilled by the hub; spilled inbound text (`content.truncated`) is rehydrated from its spill attachment through `HubApi.fetchBlob`.
- **Attachments** are not passed to agents in P1/P2 (neither backend takes them through its CLI): a relayed message with attachments gets one line `[attachments not forwarded: name (sha256 12), …]`.
- **Ports:** tests listen on port 0. Never use 45752 or 49575.

## Review Focus

1. **Exactly once across crashes.** A redelivered `job_request`, a replay after a cursor reset, and a daemon kill between `backend.launch()` and recording the `SessionRef` each give one session (intent row + `findByTag`). A kill mid-turn posts that turn's reply exactly once (outbox + `turns` row + resumable `turns()` cursor). A session that cannot be found after restart ends `failed {error: "outcome_unknown"}` and is never relaunched. Pinned in Tasks 9, 14 and 18.
2. **Who reaches the agent.** Only the requester, the operator and `relay_from` peers are relayed; anyone else gets `processed` with note `not_relayed` and no reply. Controls, question answers and `launch.decision` are accepted only from the senders [D] §3.4–3.6 name. A prompt cannot pick a path (projects are aliases), widen its ceiling or choose its approvers. Pinned in Tasks 10, 11 and 12.
3. **Approvals cannot be spoofed or lost.** Only the addressee (enforced by the hub) or the operator override resolves a prompt. A parent expiry resolves to the backend's deny option (or escalates, by config). Escalation keeps the same `launch.permission`. After an override the parent gets `launch.approval_closed`, and a late parent answer gets a superseded note. `launch.permission` validates against its closed schema and stays under 6 KiB. Pinned in Tasks 8 and 12.
4. **Issue 28 cannot widen a principal's power.** Default off; `operator`, `source`, `session` and `dot` are never provisionable; the cap counts active peers only, re-enable counts toward it, and `--creates-per-hour` bounds create/disable loops; a principal touches only peers it created and still owns; created peers inherit the principal's default scopes, so a scoped principal cannot mint an unscoped peer; a replay never meets a limit refusal. Pinned in Tasks 2 and 3.
5. **Idle never kills live work.** Park or settle happens only when no turn, approval, question, buffered or native-queued input, or observable background task is open, and no relayed message arrived in the window. Opaque backends use the longer settle timer and say so. Paseo settle never removes work. Pinned in Tasks 13 and 16.
6. **Bridges stay unmodified and isolated.** The `t3` plugin uses only `t3-bridge` subcommands that exist today, so it neither appends Grok Bot wake instructions nor registers watcher wakes. The sweep never touches a thread or agent without the `vl-` tag. Pinned in Tasks 14, 15 and 16.

- **Questions** ([D] §3.4):
  - `onQuestion` with a secret question → resolve `"secrets cannot be provided through vecnet"` at once and post a note.
  - Otherwise post a `launch.question` message (key `vl.q.…`, priority `wake`, to the requester) and record the row once `onSent` returns its `message_id`.
  - A reply `in_reply_to` that message from the requester, the operator or a `relay_from` peer answers it: `launch.answers` when present and valid, else the text, matched case-insensitively to an option label, or taken as free text where `allow_other`.
  - A blocking question times out after `questions.blocking_timeout_ms` with `"no answer from requester; use your best judgement and say what you assumed"` and a note. A non-blocking question resolves the same way when its signal aborts.
  - The reply is consumed, never relayed as turn input, and gets a `processed` receipt.
- **Permission prompts** ([D] §3.5, §4.2):
  - `onPermissionRequest` runs `finishPermission`, then `route`.
  - `requester` / `relay`: an `approval_request` in the job thread to the requester (key `vl.ar.<apr>`, options = the backend labels plus `escalate` if `escalateOption`, `escalate_to_operator` from the route, `expires_at` = now + `parentExpiresMs`, priority `wake`, `metadata["launch.permission"]`, `question` = the request summary capped at 512 chars).
  - `operator`: the same in the job's escalation thread (`ledger.escalationThread`, created on first use with key `vl.es.<job>.<n>`), with backend options only and `operator_expires`.
  - **Resolution:**
    - An `approval_response` from the addressee with a backend label → that option, recorded with `decided_by`, `decided_via` (from `launch.decided_via`) and latency.
    - `escalate` → a new operator prompt with the same `launch.permission` and `launch.escalated_from`; the row becomes `escalated`.
    - Hub `expired`, or the launcher's own timer at `expires_at` (whichever comes first) → `defaultOnExpiry`, or escalate when `onParentExpiry` says so.
    - An operator reply `in_reply_to` the prompt carrying `launch.decision` (a valid label) → that option, then a `launch.approval_closed` notice to the requester (key `vl.ac.<apr>`).
    - A later parent answer gets a "superseded" note (key `vl.nt.<job>.superseded.<n>`).
  - Labels map back to option ids from the stored row. A response naming an unknown approval → `unrelated`.

## Resolved ambiguities (recorded for Max; each is reversible)

1. **Hub client location.** The openclaw plugin has not been built, so there is no client to share yet. This plan builds `connectors/hub-client/` with openclaw's Task 1–4 interfaces, and openclaw imports it later instead of building those tasks.
2. **Tooling.** Node runs the TypeScript directly through type stripping (Node ≥ 22.18, above the design's 22.12; every surveyed host qualifies). Tests use `node:test`, so there is no vitest. Dev deps are `typescript@7.0.2` and `@types/node@22`. No pnpm workspace, so openclaw's own package stays independent.
3. **Config format** is JSON with the design's keys, because a TOML parser would be a runtime dependency.
4. **`t3` launch** uses `t3-bridge call t3_thread_launch`, an existing subcommand, rather than `t3-bridge launch`. This sets the `launch/<job_id>` branch and avoids the bridge's Grok Bot wake footer and watcher wakes. Settle uses `call t3_thread_organize`.
5. **`paseo` workspace.** The launcher creates the worktree and runs `--no-worktree`, so the branch is settable and Paseo's settle cannot delete work.
6. **Escalation** goes to a per-job thread with the operator, because a requester-locked job thread refuses a new participant.
7. **`job_status` priorities:** `hold` for accepted and running, `wake_idle` for terminal states.
8. **The `expires_at` cap** also applies to an operator reply's explicit value (it resets the TTL like a fresh message). Peer replies are unchanged.
9. **Issue 28 details:**
   - `dot` joins the never-provisionable kinds.
   - "Own peer" means `created_by` = caller and still `prn_id` = caller.
   - "Inherit the principal's default scope" is built literally, as operator-set default scopes copied at create (default empty = allow all, today's behaviour).
   - A replay returns the original stored response.
   - A replay is checked before any limit.
10. **Policy merge:** the most specific entry (peer, else principal) merged field by field over `default`; a peer entry does not also inherit a principal entry.
11. **Deferred:** H4 launches view, H6–H10 (P3), the relay breaker, `continue_job`, attachments to agents, and the opseed fixture (to keep goldens stable).
12. **P2 build boxes** run the launcher as Max's user unit, not as a `vecnet-launcher` system uid, because t3-bridge's tokens live in Max's home (D2). The dedicated uid arrives with P4.
