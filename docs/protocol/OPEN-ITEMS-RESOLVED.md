# Resolutions for PROTOCOL.md OPEN items (2026-11-01)

Decided by the coordinating agent under Max's delegation of technical choices (map Notes). Numbering follows `docs/PROTOCOL.md` §15 as first written. Items marked **(product)** touch behaviour Max might care about and are flagged to him; the rest are implementation choices.

1. **Error body.** Every non-2xx returns `{"error": {"code": "<snake_case>", "message": "<human>", "details": {…}}}`. `code` values are the reason codes listed throughout PROTOCOL.md.
2. **Status codes.** `scope_denied` 403; `unknown_recipient` 404; `name_not_an_address` 422; `unknown_blob` 422 (attachment hash not uploaded and no `origin_url`); `payload_too_large` 413 for SendRequest text over 64 KiB, metadata over 8 KiB, `job_request.input` over 16 KiB, `job_status.output` over 8 KiB, any body over 256 KiB.
3. **Idempotency conflict.** Same `idempotency_key` (per sender, 24 h window) with a different body → 409 `idempotency_conflict`. Same body → 200 with the original response.
4. **Send response.** 202 `{"message_id", "thread_id", "deliveries": [{"delivery_id", "recipient", "via", "state"}], "job_id"?: …, "spilled": bool}`. A new job's `job_id` is returned here and also appears on the Delivery as `message.job_request` is echoed unchanged plus `metadata["vecnet.job_id"]` set by the hub.
5. **Streams and cursors.** A principal credential on `GET /v1/events` receives events for all its peers by default; `?peer=<peer_id>` narrows to one. The acked cursor is per stream owner and scope (principal-wide, or per peer). Multiple concurrent consumers of the same owner+scope are allowed: they receive the same events and share one acked cursor. There are no per-consumer cursors.
6. **Receipts endpoint.** `POST /v1/receipts {"delivery_id", "state": "processed"|"read"|"failed", "note"?}` → 204. Only the delivery's recipient (or its principal) may post. MCP tool `vecnet_receipt(delivery_id, state, note?)` mirrors it. `accepted` is never posted by clients; the hub records it from 2xx or cursor acks.
7. **Blobs.** `PUT /v1/blobs?ttl=<seconds>` optional TTL (min 1 h). Over 25 MiB → 413 `blob_too_large`; over the daily quota → 429 `upload_quota_exceeded` with `Retry-After`; reading a purged blob → 410 `blob_purged`. A blob referenced by any retained message is pinned regardless of its TTL (reference wins; TTL applies only while unreferenced).
8. **Threads API.** `GET /v1/threads?participant=me|<peer_id>&group=<id>&since=<timestamp>&limit=<n≤200>` → `{"threads": [ThreadSummary…], "next": <opaque>}`. `GET /v1/threads/{id}/messages?after=<message_id>&limit=<n≤200>` → `{"messages": [Message…], "next_after": <message_id|null>}`; `after` is exclusive; omitted means from the start. Participants only (403 `not_participant`).
9. **Ingress.** Accepted → 202 `{"message_id"}`; bad signature → 401 `bad_signature`; oversize → 413. Source messages default to `priority: wake_idle`, configurable per source. Redelivery dedupe key is `(source_id, provider delivery id)` (GitHub `X-GitHub-Delivery`); a repeat returns the original `message_id`. Source→thread: one thread per `(source_id, origin.thread_id)`, created on first event, title from the first payload.
10. **Principals.** `vecnet principal add --name <n>` → `prn_…` plus its credential. `vecnet peer add … --principal <prn_>` assigns. `peer add` without `--principal` creates an implicit single-peer principal with the same display name. `vecnet peer move <peer> --principal <prn_>` reassigns (operator only).
11. **Push limits.** Push body cap 256 KiB (a Delivery with 16 attachment references and 4 KiB text fits comfortably). 409 → delivery `failed`, operator alerted, never retried. 3xx is not followed and is terminal `failed`. Response bodies over 4 KiB are ignored but the status still counts.
12. **MCP revisions.** Serve 2026-07-28 and 2025-11-25. Older `initialize` protocol versions are rejected with the newest supported version in the error.
13. **Tool set.** `vecnet_send`, `vecnet_reply(message_id, text, priority, …)` (sugar: derives `thread_id` and `in_reply_to`), `vecnet_inbox(after?, limit?)`, `vecnet_ack(cursor)`, `vecnet_receipt`, `vecnet_presence`, `vecnet_threads`, `vecnet_thread(id, after?)`, `vecnet_peers`. Inbox resource URIs: `vecnet://peer/<peer_id>/inbox` and `vecnet://principal/<prn_id>/inbox`.
14. **Events profile mapping.** `eventId` = `delivery_id` for `delivery` events, else the log cursor string. The Events `cursor` is the log cursor. Event types pushed to a dot: `delivery` by default; `receipt`, `thread_updated`, `approval_expired` only if the subscribe arguments include `types`. OpenAI's Secure MCP Tunnel is **unsupported** in v1; public HTTPS is the path.
15. **OAuth.** The hub's authorization server publishes RFC 8414 metadata and RFC 9728 resource metadata, supports PKCE S256, Dynamic Client Registration (RFC 7591) and CIMD. Link-code flow: operator runs `vecnet peer link <peer>` → an 8-character code (12 since 2026-11-04, PROTOCOL §20.1) valid 10 minutes; the consent page on the principal's first login asks for it and binds the principal to the peer. Access tokens 1 h, refresh tokens 30 d, rotated on use. `/mcp` accepts either a vecnet bearer (peer or principal secret) or an OAuth token. Grok Bots reach `/mcp` with a peer bearer configured in the bot's MCP settings.
16. **`wake_idle` mechanics (product).** A held `wake_idle` delivery is pushed once when the recipient's presence later becomes `idle` or stale (`unknown` counts as idle). Priority affects only push transports and the operator's notification webhooks; SSE and MCP pull consumers, and `vecnet watch`, see every event as it is appended. For dots, `hold` and non-idle `wake_idle` mean "no Events push"; the delivery is still readable via `vecnet_inbox`.
17. **Duplicate paths.** One Delivery per `(message_id, recipient)`. `via` names the first group that resolved to the recipient; any others are listed in the Delivery-level field `also_via` (array of group ids), never in message metadata, so the Message stays byte-identical across recipients. (Corrected after the fold-in flagged the conflict.)
18. **Dead-letter retry.** Operator retry keeps the same `delivery_id`, continues the `attempt` counter, and grants a fresh budget of 8 attempts.
19. **Jobs.** Hub job states: `requested` on creation, then w2m's table (`accepted`, `running`, `succeeded`, `failed`, `cancelled`; `cancellation_requested` when the requester posts a `job_status` with `state: cancelled` while the job is not terminal). A `job_request` requires exactly one peer recipient (groups → 422 `job_single_recipient`). Only that recipient (or its principal) may report; others → 403. A stale or equal `sequence` → 409 `stale_sequence` and the report is not delivered.
20. **Budget and depth accounting (product).** Approval requests, approval responses and job status messages are messages and count against the thread budget and increment depth like any reply. Hub-posted messages (expiry responses) count against neither.
21. **Groups and participants.** Sending to an archived group → 410 `group_archived` (the operator can unarchive). `ThreadSummary.group` is the group named as the first recipient when the thread was created, else null. A thread holds at most 64 participants; a send that would exceed it → 422 `thread_full`.
22. **Presence subscription and directory events.** `subscribe_presence` is set with `PATCH /v1/peers/me {"subscribe_presence": "all"|"teams"|"none"}` and `vecnet presence subscribe <value>`. `directory_updated` goes to every peer; `data` is `{"peer_id", "change": "enrolled"|"updated"|"removed", "fields": [names]}`.
23. **Hub-authored messages and notifications.** The hub's expiry `approval_response` has `sender: "hub"` (the `actorId` schema gains the constant `"hub"`). An approval response to a closed approval → 422 `approval_closed`; an option not in the request → 422 `invalid_option`. Notification webhook payload is the Event JSON, signed with Standard Webhooks using that notification route's own `whsec_`.
24. **Read scopes.** Scopes gate sends and group creation only. Every peer may read the directory. Thread history is readable by participants only.
25. **Connector placement.** The Grok Bot push is an in-hub push route of kind `grokbot` (bearer POST of the Delivery to the routine URL); no separate process. `origin` stays null for Grok Bot traffic because the vecnet ids ride in the body and are echoed. openclaw: one openclaw session per vecnet thread; `processed` = the dispatch completed; mention gating is a plugin config option (default off: every delivery dispatches).
26. **Reserved metadata.** A SendRequest containing any `metadata` key starting with `vecnet.` → 422 `reserved_metadata`.
27. **Source drift fixed in this commit.** Example 04's comment now says escalation at the halfway point and that it is phase 2. `GLOSSARY.md` was already rewritten for principals, three priorities, depth, origin and reachability; its directory entry now says the hub reads presence only for `wake_idle` and never verifies it.

## Amendments from pag-chat's PROTOCOL.md review (2026-11-01)

28. **Operator replies reset depth; default `max_depth` 32.** Decisive error in R20 as written: a human and a bot in one thread were cut off after 16 exchanges. See PROTOCOL.md §16.1.
29. **Per-peer rate limits** (60 sends/min, 20 new threads/hour, 429 `rate_limited`, operator-adjustable, audited). Decisive error: the thread budget bounded one thread but a runaway bot could open unbounded threads. §16.2.
30. **`history_access` default `from_join`, `locked_participants` flag, blob reads gated by message visibility.** Decisive error: any participant could leak a whole thread plus blobs by addressing one new peer. This changes Max's round-3 default (late joiners get full history); flagged to Max for veto. §16.3.
